### Statement Parsing: The Dispatcher Pattern

**Core difference from expressions:**
- Expressions have **value** (evaluated to result)
- Statements have **effect** (change program state)

**Implementation pattern:**

```python
def parse_statement(self):
    """Dispatcher: look ahead to determine statement type"""
    if self.match(IF):
        return self.parse_if_statement()
    elif self.match(WHILE):
        return self.parse_while_statement()
    elif self.match(RETURN):
        return self.parse_return_statement()
    elif self.match(VAR):
        return self.parse_var_declaration()
    elif self.match(LBRACE):
        return self.parse_block()
    else:
        # Expression statement or assignment
        return self.parse_expression_statement()
```

**Why this works:**
- First token **uniquely determines** statement type
- No backtracking needed (grammar is LL(1) for statements)
- Dispatcher delegates to specialized parsers

**Chess analogy:** Like move generation—piece type determines legal moves. Token type determines parsing function.

### Lookahead and Commitment

**The fundamental tradeoff:**
- **Commit early:** Fast, but may fail on legal input
- **Backtrack freely:** Correct, but slow

**Our approach:** Use **minimal lookahead** to commit correctly.

#### Example: Assignment vs. Expression Statement

```
x + 3;        // Expression statement
x = 5;        // Assignment statement
```

Both start with identifier. How to distinguish?

**Solution: Look ahead one token after identifier**

```python
def parse_expression_statement(self):
    """Handle both assignment and expression statements"""
    # Save position in case we need to backtrack
    start_pos = self.position
    
    # Try to parse as assignment
    if self.match(ID):
        name = self.current_token.value
        self.advance()
        
        if self.match(ASSIGN):
            # It's an assignment!
            self.advance()
            value = self.parse_expression()
            self.expect(SEMICOLON)
            return AssignmentStatement(name, value)
        else:
            # Not assignment, backtrack and parse as expression
            self.position = start_pos
            expr = self.parse_expression()
            self.expect(SEMICOLON)
            return ExpressionStatement(expr)
    else:
        # Must be expression
        expr = self.parse_expression()
        self.expect(SEMICOLON)
        return ExpressionStatement(expr)
```

**Pattern:**
1. Peek ahead to disambiguation point
2. Commit to interpretation
3. If wrong, backtrack and retry

**AoC analogy:** Like trying BFS before DFS—measure first, then optimize based on actual input patterns.

### Function Calls: The Parentheses Problem

**Challenge:** Distinguish function calls from grouping.

```
foo(x)        // Function call
(x) + 3       // Grouping in expression
```

**Solution:** Context determines meaning.

```python
def parse_primary(self):
    """Primary → INT | ID | FunctionCall | '(' Expr ')'"""
    
    if self.match(INT):
        value = self.current_token.value
        self.advance()
        return IntLiteral(value)
    
    elif self.match(ID):
        name = self.current_token.value
        self.advance()
        
        # Is this a function call?
        if self.match(LPAREN):
            # Yes! Parse argument list
            self.advance()
            args = []
            if not self.match(RPAREN):
                args.append(self.parse_expression())
                while self.match(COMMA):
                    self.advance()
                    args.append(self.parse_expression())
            self.expect(RPAREN)
            return FunctionCall(name, args)
        else:
            # Just an identifier
            return Identifier(name)
    
    elif self.match(LPAREN):
        # Grouping
        self.advance()
        expr = self.parse_expression()
        self.expect(RPAREN)
        return expr
    
    else:
        self.error("Expected primary expression")
```

**Key insight:** Identifier followed by `(` **must** be function call. Context (what comes after ID) determines interpretation.

### Grammar Stratification: Precedence Without Tables

**Problem:** How to encode operator precedence in grammar?

**Solution:** **Stratify** grammar into levels, one per precedence level.

```
Program      → FunctionDecl* Statement*
FunctionDecl → 'fn' ID '(' ParamList? ')' Block
Statement    → IfStmt | WhileStmt | ReturnStmt | VarDecl | Block | ExprStmt

Expression   → Assignment
Assignment   → LogicalOr ('=' Assignment)?
LogicalOr    → LogicalAnd ('||' LogicalAnd)*
LogicalAnd   → Equality ('&&' Equality)*
Equality     → Comparison (('==' | '!=') Comparison)*
Comparison   → Addition (('<' | '>' | '<=' | '>=') Addition)*
Addition     → Multiplication (('+' | '-') Multiplication)*
Multiplication → Unary (('*' | '/') Unary)*
Unary        → ('!' | '-') Unary | Primary
Primary      → INT | ID | FunctionCall | '(' Expression ')'
```

**Each level:**
- Handles operators at that precedence
- Calls next level down for higher precedence
- Left-recursive operators become loops (for left associativity)
- Right-recursive operators become recursion (for right associativity)

**Example: Assignment is right-associative**

```python
def parse_assignment(self):
    """Assignment → LogicalOr ('=' Assignment)?"""
    node = self.parse_logical_or()
    
    if self.match(ASSIGN):
        self.advance()
        # Right recursion for right associativity!
        right = self.parse_assignment()
        node = Assignment(node, right)
    
    return node
```

Result: `x = y = 3` parses as `x = (y = 3)` ✓

**Chess analogy:** Like evaluation hierarchies—material > position > king safety. Each level builds on the one below.

### Scope Tracking (Minimal Version)

We add **basic scope tracking** to catch obvious errors during parsing:

```python
class Parser:
    def __init__(self, tokens):
        self.tokens = tokens
        self.position = 0
        self.scopes = [{}]  # Stack of scopes
    
    def enter_scope(self):
        """Enter new block scope"""
        self.scopes.append({})
    
    def exit_scope(self):
        """Exit current block scope"""
        self.scopes.pop()
    
    def declare_variable(self, name):
        """Declare variable in current scope"""
        if name in self.scopes[-1]:
            self.error(f"Variable {name} already declared in this scope")
        self.scopes[-1][name] = True
    
    def parse_block(self):
        """Block → '{' Statement* '}'"""
        self.expect(LBRACE)
        self.enter_scope()  # New scope!
        
        statements = []
        while not self.match(RBRACE) and not self.at_end():
            statements.append(self.parse_statement())
        
        self.expect(RBRACE)
        self.exit_scope()  # Exit scope
        
        return Block(statements)
```

**What this catches:**
- Redeclarations in same scope: `{ var x = 1; var x = 2; }` ✗
- Basic scope violations

**What it doesn't catch (yet):**
- Use before declaration: `x = 3;` (no var x)
- Cross-scope references
- Type mismatches

**Why minimal?** Full semantic analysis is separate phase. Parser just catches **obvious structural errors**.

### The Complete Language Grammar

```
// Top level
Program      → (FunctionDecl | Statement)*
FunctionDecl → 'fn' ID '(' ParamList? ')' Block
ParamList    → ID (',' ID)*

// Statements
Statement    → VarDecl | IfStmt | WhileStmt | ReturnStmt | Block | ExprStmt
VarDecl      → 'var' ID ('=' Expression)? ';'
IfStmt       → 'if' '(' Expression ')' Statement ('else' Statement)?
WhileStmt    → 'while' '(' Expression ')' Statement
ReturnStmt   → 'return' Expression? ';'
Block        → '{' Statement* '}'
ExprStmt     → Expression ';'

// Expressions (stratified by precedence)
Expression   → Assignment
Assignment   → LogicalOr ('=' Assignment)?
LogicalOr    → LogicalAnd ('||' LogicalAnd)*
LogicalAnd   → Equality ('&&' Equality)*
Equality     → Comparison (('==' | '!=') Comparison)*
Comparison   → Addition (('<' | '>' | '<=' | '>=') Addition)*
Addition     → Multiplication (('+' | '-') Multiplication)*
Multiplication → Unary (('*' | '/') Unary)*
Unary        → ('!' | '-') Unary | Primary
Primary      → INT | FLOAT | STRING | BOOL | ID | FunctionCall | '(' Expression ')'
FunctionCall → ID '(' ArgList? ')'
ArgList      → Expression (',' Expression)*
```

**Properties:**
- LL(1) for all constructs (except assignment/expression-statement ambiguity, resolved with 2-token lookahead)
- No left recursion
- Precedence encoded structurally
- Associativity follows from recursion pattern

### Design Decisions

1. **Why stratified grammar?**
   - Precedence embedded in structure
   - No operator precedence table needed
   - Natural left/right associativity

2. **Why minimal scope tracking in parser?**
   - Catch obvious errors early
   - Full semantic analysis is separate phase
   - Keep parser focused on syntax

3. **Why lookahead limited to 2 tokens?**
   - LL(2) sufficient for this grammar
   - More would indicate grammar problem
   - Real parsers (GCC, Clang) use LL(2) or LR(1)

4. **Why no automatic semicolon insertion?**
   - Explicit is better than implicit
   - Avoids JavaScript-style pitfalls
   - Easier to implement and reason about

## Insights

### 1. Grammar Stratification is Precedence Encoding

**The revelation:** Operator precedence tables are **implicit** in stratified grammars. Each level encodes one precedence tier.

**Why this matters:** Hand-written parsers don't need separate precedence tables—the call structure **is** the precedence.

**Chess connection:** Like material values (P=1, N=3, B=3, R=5, Q=9)—hierarchy emerges from structure, not external table.

---

### 2. Statements vs. Expressions: Effect vs. Value

**The distinction:**
- Expressions **compute** (return value)
- Statements **perform** (cause effect)

**In practice:** Many statements contain expressions (if condition, while condition, return value). The AST reflects this nesting.

**Why both exist:** Languages need computation (expressions) and control flow (statements). Purely functional languages unify these (everything is expression).

---

### 3. Lookahead as Commitment Strategy

**The pattern:**
- Look ahead minimum tokens to distinguish cases
- Commit to interpretation
- Backtrack only if necessary

**Production compilers:** Most use 1-token lookahead (LL(1)). When that's insufficient, they refactor grammar or use 2-token lookahead in specific spots.

**Like chess:** Minimal lookahead that avoids blunders. Deep search (backtracking) only when position is complex.

---

### 4. Parser Scope Tracking is Opportunistic

**What we learned:** Parser **can** track scopes, but **shouldn't** do full semantic analysis.

**The boundary:**
- Parser catches: structural errors, obvious redeclarations
- Semantic pass catches: use-before-def, type errors, undefined references

**Why separate?** Semantic analysis needs **complete** AST. Parser builds it incrementally.

---

### 5. Testing Mirrors Grammar Structure

**The correspondence:**
- Grammar has production rules → Tests have cases per rule
- Grammar has precedence levels → Tests verify precedence
- Grammar has ambiguity spots → Tests verify disambiguation

**Like perft:** Grammar is spec, tests are checksum. If test coverage matches grammar structure, you've tested everything.

## Questions Raised

### 1. When should parser do semantic checks vs. deferring to later pass?

**Current answer:** Parser checks **structure** (syntax), semantic pass checks **meaning** (types, scopes, definitions).

**Gray area:** Some things (like detecting redeclarations in same scope) are borderline. We chose to catch them early because it's trivial during parsing.

**Investigate:** How do production compilers draw this boundary? What are the tradeoffs?

---

### 2. How do real compilers handle more complex disambiguation?

**Our approach:** LL(2) lookahead + limited backtracking.

**Real compilers:** Some use LR parsing (bottom-up), some use GLR (generalized LR for ambiguous grammars), some use PEG (parsing expression grammars with ordered choice).

**Question:** When does LL parsing break down? What patterns force you to more powerful techniques?

---

### 3. How to balance grammar simplicity vs. language expressiveness?

**Tradeoff:** Simple grammar → easy to parse, but may restrict language features. Complex grammar → powerful language, but harder to parse.

**Example:** C++ is notoriously hard to parse because grammar is complex (templates, operator overloading, context-sensitive syntax).

**Question:** Can you design languages to be both expressive and easy to parse? (Rust tries this with its macro system.)

---

### 4. Should AST preserve all syntactic detail or normalize?

**Our AST:** Preserves some detail (grouping parens implicit in structure) but normalizes others (precedence via nesting).

**Alternative:** CST (Concrete Syntax Tree) preserves **everything**, including whitespace and comments.

**Question:** When do you need CST vs. AST? (Answer: Refactoring tools and formatters need CST, compilers use AST.)
