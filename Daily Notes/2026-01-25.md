## Lectures Documented

### [Lecture 23: Abstract Syntax Trees](../Stanford/lecture-23-abstract-syntax-trees.md) – Discarding Irrelevant Detail

**Core insight:** Parse trees contain too much information; ASTs keep only what matters for semantics.

- **Parse tree problem:** Every grammar detail preserved (parentheses, precedence markers, intermediate nodes)
- **AST solution:** Strip to meaningful structure only—operators, operands, control flow
- **Size difference:** Parse trees 2-3× larger than ASTs for typical expressions
- **Why it matters:** Smaller trees → faster traversal, less memory, clearer semantics
- **Implementation:** Build AST directly during parsing (don't build parse tree first)

**Key principle:** Parsing produces structure; AST is that structure without grammatical scaffolding.

**Chess analogy:** Parse tree is move notation (1. e4 e5 2. Nf3); AST is board position (what matters for evaluation).

### [Lecture 24: Recursive Descent Parsing](../Stanford/lecture-24-recursive-descent-parsing.md) – Top-Down Strategy

**Core insight:** Build parse tree from root down by having each nonterminal become a function that tries alternatives.

- **Top-down means:** Start with start symbol, expand toward terminals (opposite of bottom-up)
- **Left-to-right means:** Process tokens in order, never skip ahead
- **One-token lookahead:** Peek at current token to decide which production to try
- **Backtracking:** If production fails, restore position and try next alternative
- **The mapping:** Nonterminal → function; production → code path; grammar → call graph

**Detailed example:** Parsing `(5)` with grammar `E → T | T + E`, `T → int | (E)`
- 12-step walkthrough showing function calls, token matching, success/failure paths
- Call stack visualization at each decision point
- Backtracking mechanics when `T → int` fails on `(`

**Why top-down:** Intuitive (matches how humans read), easy to hand-write, integrates semantic actions naturally.

### [Lecture 25: Recursive Descent Algorithm](../Stanford/lecture-25-recursive-descent-algorithm.md) – The General Implementation

**Core insight:** Systematic translation from grammar to code using two-tier structure: production functions + dispatchers.

**The Algorithm:**
- **Token type enum:** All terminal symbols
- **Global `next` pointer:** Current position in token stream
- **`match(token)` semantics:** Check and advance `next` (ALWAYS advances, even on failure!)
- **Production functions:** One per production (e.g., `e1()`, `e2()`, `t1()`)
- **Dispatcher functions:** One per nonterminal (e.g., `e()`, `t()`), tries alternatives with save/restore

**Critical detail:** `match()` side effect requires explicit save/restore:
```c++
bool t() {
  Token* save = next;
  if (t1()) return true;
  next = save;  // Must restore after failure
  if (t2()) return true;
  next = save;
  if (t3()) return true;
  return false;
}
```

**Detailed trace:** Parsing `(5)` with 12-step execution showing:
- `next` pointer state at each step
- Save/restore discipline
- Short-circuit semantics (`&&` stops on false)
- How backtracking works locally within dispatchers

**Production functions are simple:** Just chain `match()` and nonterminal calls with `&&`.

**Dispatcher complexity:** All backtracking logic lives here (save before trying, restore after failure).

### [Lecture 26: Recursive Descent Limitation](../Stanford/lecture-26-recursive-descent-limitation.md) – Commitment Problem

**Core insight:** Simple RD commits to the first successful production and cannot backtrack later, even if overall parse fails. This makes it not fully general.

**The failure case:**
- Grammar: `T → int | int * T`
- Input: `int * int`
- What happens: `t()` matches `T → int`, returns success, consumes first `int`
- Problem: `parse()` discovers unconsumed input (`* int`), but `t()` already exited—can't retry `T → int * T`

**Two-level backtracking:**
1. **Within nonterminal (works):** Dispatcher tries alternatives, restores position on failure
2. **Across nonterminals (fails):** Once a nonterminal returns success, decision is final—no mechanism to re-enter and retry

**Call stack showing commitment:**
```
parse() → e() → e1() → t() → t1() SUCCESS → returns all the way
                                     ↑
                           COMMITMENT POINT
parse() checks EOF → FAILS, but t() is gone, can't retry
```

**The sufficient condition:** Algorithm works when "at most one production per nonterminal can succeed" in any context. If this holds, commitment is safe.

**The fix: Left factoring:**
```
Before: T → int | int * T
After:  T → int T'
        T' → ε | * T
```

Now `T` always matches `int` first, then `T'` decides whether to continue. No ambiguity at decision points.

**Real-world:** GCC, Clang, Rust carefully design grammars to avoid commitment problems (via left factoring).

**Chess analogy:** Like a chess engine that commits to the first plausible move without considering siblings—if deep search reveals it's losing, can't go back. Fix: refactor so first move is always right (like left factoring).

### [Lecture 27: Left Recursion](../Stanford/lecture-27-left-recursion.md) – The Infinite Loop Problem

**Core insight:** Left-recursive grammars cause RD parsers to loop infinitely because they recurse without consuming input.

**Minimal example:**
```
Grammar: S → S a | b
```

**Naive code:**
```c++
bool s() {
  Token* save = next;
  if (s() && match('a')) return true;  // IMMEDIATE RECURSION
  ...
}
```

**What happens:**
- `s()` calls `s()` without advancing `next`
- Second `s()` calls `s()` again (same position!)
- Third `s()` calls `s()` again...
- **Stack overflow**—no forward progress ever made

**Why right recursion works:**
```
Grammar: S → a S | b
Code:    if (match('a') && s()) ...  // Consumes 'a' BEFORE recursing
```

Each recursive call sees different state (input consumed), so termination is possible.

**The transformation algorithm:**

**Direct left recursion:** `A → A α | β`

**Transform to:**
```
A → β A'
A' → α A' | ε
```

**Example:**
```
Before: Expr → Expr + Term | Term
After:  Expr → Term Expr'
        Expr' → + Term Expr' | ε
```

**Indirect left recursion:** `A ⇒+ A α` through intermediate steps

**Detection:** Build derivation graph, find cycles

**Elimination:** Systematic substitution + direct elimination at each step

**Associativity note:** Left recursion gives left-associative trees; right recursion requires extra work to recover left-associativity during semantic analysis.

**Real-world examples:**
- **GCC:** Right-recursive grammar throughout
- **Rust:** Pratt parsing for expressions (handles associativity naturally, no transformation)
- **Python pre-3.9:** Hand-transformed to right recursion
- **Python 3.9+:** PEG parser (memoization handles left recursion)

**Chess analogy:** Like infinite search—engine tries to analyze same position repeatedly without making moves. Fix: ensure every search makes at least one move (consume input before recursing).

### [Lecture 28: Recursive Descent Summary](../Stanford/lecture-28-recursive-descent-summary.md) – Synthesis and Practice

**Core insight:** Despite limitations, simple RD is widely practical because grammars can be refactored to fit constraints, and the result is simple, debuggable, and efficient.

**What RD is:**
- **Top-down parsing:** Root → leaves construction
- **Function per nonterminal:** Direct grammar → code mapping
- **Backtracking via save/restore:** Local to each dispatcher
- **Mechanical translation:** Systematic, predictable

**The two limitations:**

1. **Commitment (lecture 26):** Can't backtrack across nonterminal returns → requires "at most one production succeeds" property
2. **Left recursion (lecture 27):** Causes infinite loops → requires elimination transformation

**The refactoring toolkit:**

1. **Left recursion elimination:** `A → A α | β` becomes `A → β A'`, `A' → α A' | ε`
2. **Left factoring:** `A → α β₁ | α β₂` becomes `A → α A'`, `A' → β₁ | β₂`
3. **Precedence stratification:** Separate grammar layers for operator precedence

**Real-world practice:**

**GCC (C/C++):**
- Hand-written RD, no parser generator
- Grammar carefully designed to avoid left recursion
- Custom error recovery with excellent diagnostics
- **Why:** Debuggability, flexibility, no tool dependencies

**Clang (LLVM C++):**
- Hand-written RD with Pratt parsing for expressions
- Clean separation: parsing vs semantic analysis
- **Benefit:** Extensible (language extensions easy to add)

**Rust (rustc):**
- Switched from generator to hand-written RD
- Pratt parsing handles precedence elegantly
- **Why switch:** Flexibility for macros, better error messages

**Python:**
- **Pre-3.9:** Hand-written RD with right-recursive grammar
- **3.9+:** PEG parser with packrat (memoization)
- **Why switch:** Grammar maintenance burden, left recursion support

**Comparison of approaches:**

| Approach | Complexity | Grammar Constraints | Performance | Use Case |
|----------|------------|---------------------|-------------|----------|
| Simple RD | Low | No left recursion | Fast | Most hand-written parsers |
| Backtracking RD | Medium | No left recursion | Exponential worst | Complex grammars |
| Packrat | Medium | None | Linear, high memory | PEG parsers |
| Pratt | Low | None | Fast | Expression parsing |
| Generators | Low | LR constraints | Fast | Stable grammars |

**Strengths of simple RD:**
- Simplicity: mechanical translation
- Debuggability: direct code correspondence
- Flexibility: easy semantic action integration
- Performance: predictable, no exponential backtracking
- Error messages: custom, context-aware
- No tool dependencies

**When to use simple RD:**
- New language implementation
- Evolving specifications
- Team prefers hand-written code
- Debuggability prioritized

**Alternatives when:**
- Grammar very complex
- Team has generator expertise
- Stable specification
- Separation of grammar/code desired

**Historical perspective:**
- **1970s-80s:** Parser generators dominant (yacc, bison)
- **1990s-2000s:** Hand-written RD re-emerges (GCC, Clang)
- **2010s-present:** Hybrid approaches (Pratt, PEG, incremental)

**The meta-lesson:** Simple RD trades grammar generality for code simplicity. The trade is worth it because most real grammars can be refactored to fit.

## Key Insights Across All Lectures

### 1. **Parse Trees vs ASTs: Discard What Doesn't Matter**

Parse trees preserve every grammatical detail; ASTs keep only semantic structure. Build ASTs directly during parsing—don't construct parse trees first. Like keeping chess board positions, not move notation.

### 2. **Top-Down Parsing is Intuitive**

RD mirrors how humans read: start with overall structure (statement), drill down to details (operators, operands). The function call stack IS the derivation stack. Natural mental model.

### 3. **The Algorithm is Mechanical**

Grammar → code translation is systematic:
- Nonterminal → dispatcher function
- Production → production function
- Alternative → try with save/restore

No creativity required for translation—only for grammar design.

### 4. **Backtracking Has Two Scopes**

**Local (within nonterminal):** Works perfectly—try alternatives, restore on failure

**Global (across nonterminals):** Doesn't work in simple RD—commitment is final

Understanding this distinction explains both the power and limitations.

### 5. **Left Recursion is Fatal, Not Just Limiting**

- Commitment limitation → wrong rejection (annoying but recoverable via testing)
- Left recursion → infinite loop (program hangs/crashes—unacceptable)

Grammar MUST eliminate left recursion. Not optional.

### 6. **Grammar Design is Engineering**

Grammars aren't just mathematical specs—they're **engineering artifacts** optimized for:
- Parser algorithm constraints (no left recursion)
- Disambiguation (left factoring)
- Precedence (stratification)
- Readability and maintainability

Like IR design: form follows function.

### 7. **Simple Beats Complex in Practice**

Despite theoretical limitations:
- GCC, Clang, Rust use simple RD
- Careful grammar design makes it work
- Simplicity enables debuggability

Same pattern as linear scan register allocation: simple algorithm + good preparation beats complex general algorithm.

### 8. **Refactoring Grammars ≈ Optimizing IRs**

Left recursion elimination is grammar transformation, like SSA construction is IR transformation. Both:
- Preserve language/semantics
- Enable simpler algorithms
- One-time engineering cost, ongoing benefit
