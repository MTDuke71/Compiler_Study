## Session Notes

### The Central Insight

**There is no perfect compiler design.** Every choice is a tradeoff between competing goals.

Key realization: The "best" design depends entirely on context:
- What are you optimizing for? (Speed? Memory? Simplicity? Debuggability?)
- What constraints do you have? (Time? Target architecture? Language semantics?)
- What phase of development? (Learning? Prototyping? Production?)

Just like chess engines make different tradeoffs (search depth vs. evaluation quality vs. time per move), compilers balance:
- Compile time vs. runtime performance
- Memory usage vs. speed
- Simplicity vs. generality
- Early error detection vs. flexibility

**Important:** Multiple representations aren't redundant—they're necessary because each optimizes for different operations.

### Fundamental Tradeoffs

**1. Compile Time vs. Runtime Performance**
- More analysis = better code but slower builds
- Debug builds: optimize for compile speed (no opts, fast feedback)
- Release builds: optimize for runtime (aggressive opts, take the time)
- JIT compilers: must balance both (can't stall app startup)

**2. Memory Usage vs. Speed**
- Caching saves recomputation but costs memory
- Hash tables: O(1) lookup, ~2x memory overhead
- Arrays: O(log n) search, minimal memory
- Decision: depends on data size and access patterns

**3. Simplicity vs. Generality**
- Linear scan register allocation: simple, 95% as good as optimal
- Graph coloring: complex, near-optimal quality
- Both are valid choices for different contexts!

**4. Early Detection vs. Flexibility**
- Strict type checking catches bugs early but requires more annotations
- Permissive checking is faster to write but bugs slip to runtime
- This is language philosophy, not a technical winner

**5. Representation Choice**
- AST: great for structure, bad for control flow analysis
- TAC: great for codegen, bad for high-level transformations
- CFG: great for optimization, bad for initial generation
- SSA: great for data flow, high construction cost

### Representations and Their Strengths

**Why we need multiple IRs:**

| Representation | Best For | Worst For |
|----------------|----------|-----------|
| AST | Preserving source structure, local transforms | Control flow, global optimization |
| TAC | Simple codegen, easy to read | Representing loops, finding basic blocks |
| CFG | Control flow analysis, loop detection | Initial construction, expression structure |
| SSA | Data flow, many optimizations | Construction cost, phi elimination |

**Key insight:** Successful compilers use a pipeline:
```
Source → Tokens → AST → TAC → CFG → SSA → Optimized IR → Assembly
```

Each transformation converts to a representation better suited for the next phase.

This is why "why not just use AST for everything?" misses the point—AST is optimized for different operations than CFG.

### Real-World Examples

**Different compilers, different tradeoffs:**

**LLVM:**
- Chose: Power and generality
- Cost: Complex, slow compilation
- Benefit: Excellent optimization, many targets
- Use case: Production optimizing compiler

**TinyCC:**
- Chose: Compilation speed
- Cost: Minimal optimization
- Benefit: Extremely fast builds
- Use case: Rapid development, scripting

The realization that simple isn't worse—linear scan in production JITs really drives home that optimal isn't always best. The chess engine parallel is strong here: you don't always need the deepest search if you can evaluate quickly and accurately.

Also: the idea that we use multiple IRs not because we're indecisive, but because each is optimized for different operations. AST vs. CFG isn't "which is better"—it's "which is better *for this task*".

**What surprised me?**

## Common Misconceptions

Start tracking misconceptions you had or commonly see:

1. **"More optimization is always better"**
   - Reality: Diminishing returns, increased compile time, potential bugs
   - -O1 gives 40% benefit, -O3 gives 70% benefit but takes 8x longer to compile

2. **"Simple implementations are inferior"**
   - Reality: Linear scan register allocation is used in production JITs (V8, HotSpot)
   - 95% as good, 10x faster, simpler to debug

3. **"There's one right way to do X"**
   - Reality: Context determines correctness
   - Hand-written parser vs. generator—both valid, different tradeoffs

4. **"Design decisions are one-time choices"**
   - Reality: Tradeoffs shift as project evolves
   - Start simple, add complexity when justified by measurement

5. **"We should use one IR throughout"**
   - Reality: Multiple IRs are necessary, not redundant
   - Each optimizes for different operations

| Symbol table | Array (O(log n)) | Hash table (O(1)) | Large programs | Hash for speed |
| Symbol table | Array | Hash table | Small scopes (<10 vars) | Array for simplicity |
| Parser | Hand-written | Generator tool | Learning compiler | Hand-written (learn more) |
| Parser | Hand-written | Generator tool | Production, stable grammar | Hand-written (better errors) |
| Register allocation | Linear scan | Graph coloring | JIT compiler | Linear scan (fast compile) |
| Register allocation | Linear scan | Graph coloring | AOT optimizer | Graph coloring (quality) |
| Error handling | Stop at first | Continue parsing | Large files, slow compile | Continue (report multiple) |
| String storage | Raw bytes | Interned strings | Many comparisons | Interned (O(1) compare) |
