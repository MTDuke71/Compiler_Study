### Grammar to Code: The Mechanical Translation

The beauty of recursive descent is that **grammar rules map directly to code**. No magic, no complex algorithms—just systematic translation.

#### Rule 1: Each Non-Terminal → One Function

**Grammar:**
```
Expr → Term (('+' | '-') Term)*
```

**Code:**
```python
def parse_expr(self):
    """Expr → Term (('+' | '-') Term)*"""
    # Implementation follows
```

**Pattern:** Function name = `parse_` + non-terminal name (lowercased).

---

#### Rule 2: Terminals → match() and advance()

**Grammar fragment:** `'+' Term`

**Code:**
```python
if self.match(PLUS):
    self.advance()
    right = self.parse_term()
```

**Pattern:**
- `match(TOKEN_TYPE)` → check current token
- `advance()` → consume token, move to next
- For required tokens: `expect(TOKEN_TYPE)` → match + advance + error if no match

---

#### Rule 3: Sequence (α β γ) → Sequential Calls

**Grammar:** `'if' '(' Expr ')' Block`

**Code:**
```python
self.expect('if')
self.expect('(')
condition = self.parse_expr()
self.expect(')')
body = self.parse_block()
return IfStatement(condition, body, ...)
```

**Pattern:** Parse left-to-right, building up components.

---

#### Rule 4: Choice (α | β) → if/elif

**Grammar:** `Factor → INT | ID | '(' Expr ')'`

**Code:**
```python
def parse_factor(self):
    if self.match(INT):
        value = self.current_token.value
        line, col = self.current_token.line, self.current_token.col
        self.advance()
        return IntLiteral(value, line, col)
    elif self.match(ID):
        name = self.current_token.value
        line, col = self.current_token.line, self.current_token.col
        self.advance()
        return Identifier(name, line, col)
    elif self.match(LPAREN):
        self.advance()
        expr = self.parse_expr()
        self.expect(RPAREN)
        return expr
    else:
        self.error("Expected factor")
```

**Pattern:** Use lookahead (first token of each alternative) to decide which branch.

---

#### Rule 5: Repetition (α*) → while Loop

**Grammar:** `(('+' | '-') Term)*`

**Code:**
```python
while self.match(PLUS) or self.match(MINUS):
    op = self.current_token.value
    line, col = self.current_token.line, self.current_token.col
    self.advance()
    right = self.parse_term()
    left = BinaryOp(op, left, right, line, col)
```

**Pattern:** Keep looping while lookahead matches. Build left-associative tree by reassigning `left`.

---

#### Rule 6: Optional (α?) → if Statement

**Grammar:** `ElsePart → 'else' Block | ε`

**Code:**
```python
else_block = None
if self.match('else'):
    self.expect('else')
    else_block = self.parse_block()
return IfStatement(condition, then_block, else_block)
```

**Pattern:** Check if optional part present; if so, parse it. Otherwise, use None.

### Complete Implementation: Expression Parser

**Grammar:**
```
Expr   → Term (('+' | '-') Term)*
Term   → Factor (('*' | '/') Factor)*
Factor → INT | ID | '(' Expr ')'
```

**AST Nodes:**
```python
class ASTNode:
    def __init__(self, line=0, col=0):
        self.line = line
        self.col = col

class IntLiteral(ASTNode):
    def __init__(self, value, line, col):
        super().__init__(line, col)
        self.value = value
    
    def __repr__(self):
        return f"IntLiteral({self.value})"

class Identifier(ASTNode):
    def __init__(self, name, line, col):
        super().__init__(line, col)
        self.name = name
    
    def __repr__(self):
        return f"Identifier({self.name})"

class BinaryOp(ASTNode):
    def __init__(self, op, left, right, line, col):
        super().__init__(line, col)
        self.op = op
        self.left = left
        self.right = right
    
    def __repr__(self):
        return f"BinaryOp({self.op}, {self.left}, {self.right})"
```

**Parser:**
```python
class RecursiveDescentParser:
    def __init__(self, tokens):
        self.tokens = tokens
        self.position = 0
        self.current_token = tokens[0] if tokens else Token(EOF, None, 0, 0)
    
    def match(self, token_type):
        """Check if current token matches type (lookahead)"""
        return self.current_token.type == token_type
    
    def advance(self):
        """Consume current token and move to next"""
        self.position += 1
        if self.position < len(self.tokens):
            self.current_token = self.tokens[self.position]
        else:
            self.current_token = Token(EOF, None, 0, 0)
    
    def expect(self, token_type):
        """Consume token if it matches, else error"""
        if not self.match(token_type):
            raise ParseError(
                f"Expected {token_type}, got {self.current_token.type} "
                f"at line {self.current_token.line}, col {self.current_token.col}"
            )
        self.advance()
    
    def error(self, message):
        """Report parse error with location"""
        raise ParseError(
            f"{message} at line {self.current_token.line}, "
            f"col {self.current_token.col}"
        )
    
    def parse_expr(self):
        """Expr → Term (('+' | '-') Term)*"""
        left = self.parse_term()
        
        while self.match(PLUS) or self.match(MINUS):
            op = self.current_token.value
            line, col = self.current_token.line, self.current_token.col
            self.advance()
            right = self.parse_term()
            left = BinaryOp(op, left, right, line, col)
        
        return left
    
    def parse_term(self):
        """Term → Factor (('*' | '/') Factor)*"""
        left = self.parse_factor()
        
        while self.match(STAR) or self.match(SLASH):
            op = self.current_token.value
            line, col = self.current_token.line, self.current_token.col
            self.advance()
            right = self.parse_factor()
            left = BinaryOp(op, left, right, line, col)
        
        return left
    
    def parse_factor(self):
        """Factor → INT | ID | '(' Expr ')'"""
        if self.match(INT):
            value = self.current_token.value
            line, col = self.current_token.line, self.current_token.col
            self.advance()
            return IntLiteral(value, line, col)
        
        elif self.match(ID):
            name = self.current_token.value
            line, col = self.current_token.line, self.current_token.col
            self.advance()
            return Identifier(name, line, col)
        
        elif self.match(LPAREN):
            self.advance()
            expr = self.parse_expr()  # Recursive call!
            self.expect(RPAREN)
            return expr
        
        else:
            self.error("Expected factor (INT, ID, or '(')")
    
    def parse(self):
        """Entry point: parse expression and expect EOF"""
        ast = self.parse_expr()
        self.expect(EOF)
        return ast
```

### Execution Trace: `3 + 4 * 5`

**Tokens:**
```
[INT(3), PLUS, INT(4), STAR, INT(5), EOF]
```

**Execution (detailed):**

```
parse()
│
├─ parse_expr()
│  │
│  ├─ parse_term()
│  │  │
│  │  ├─ parse_factor()
│  │  │  └─ match(INT) → yes → IntLiteral(3) ✓
│  │  │
│  │  └─ match(STAR/SLASH) → no → return IntLiteral(3)
│  │
│  ├─ Current: IntLiteral(3)
│  ├─ match(PLUS/MINUS) → yes (PLUS)
│  ├─ advance() → consume PLUS
│  │
│  ├─ parse_term()
│  │  │
│  │  ├─ parse_factor()
│  │  │  └─ match(INT) → yes → IntLiteral(4) ✓
│  │  │
│  │  ├─ match(STAR/SLASH) → yes (STAR)
│  │  ├─ advance() → consume STAR
│  │  │
│  │  ├─ parse_factor()
│  │  │  └─ match(INT) → yes → IntLiteral(5) ✓
│  │  │
│  │  ├─ Build: BinaryOp('*', IntLiteral(4), IntLiteral(5))
│  │  └─ match(STAR/SLASH) → no → return BinaryOp(*, 4, 5)
│  │
│  ├─ Build: BinaryOp('+', IntLiteral(3), BinaryOp(*, 4, 5))
│  └─ match(PLUS/MINUS) → no → return BinaryOp(+, 3, (* 4 5))
│
└─ expect(EOF) → success ✓
```

**Resulting AST:**
```
       BinaryOp(+)
       /          \
  IntLiteral(3)  BinaryOp(*)
                 /          \
            IntLiteral(4)  IntLiteral(5)
```

**Key observations:**
1. **Depth encodes precedence:** `*` is deeper → evaluates first
2. **Left-associativity:** Reassigning `left` in loop builds `(a + b) + c` structure
3. **Call stack mirrors grammar:** Expr → Term → Factor hierarchy
4. **Recursion at parentheses:** Factor can call Expr (mutual recursion)

### Backtracking: When and Why

**Scenario:** Grammar has overlapping alternatives (not LL(1)).

**Example (ambiguous lookahead):**
```
Stmt → ID '=' Expr ';'      // Assignment
     | ID '(' ArgList ')'   // Function call
```

Both start with `ID`. Need to look ahead further to decide.

**Without backtracking (LL(1) solution):** Left-factor.
```
Stmt → ID StmtTail
StmtTail → '=' Expr ';' | '(' ArgList ')'
```

**With backtracking (LL(k) solution):**
```python
def parse_stmt(self):
    # Save current position
    saved_pos = self.position
    saved_token = self.current_token
    
    try:
        # Try first alternative
        return self.parse_assignment()
    except ParseError:
        # Failed, restore position
        self.position = saved_pos
        self.current_token = saved_token
        
        # Try second alternative
        return self.parse_function_call()
```

**When to use backtracking:**
- Grammar cannot be easily refactored
- Need to handle ambiguous constructs (rare in programming languages)
- Prototyping (quick implementation before optimizing grammar)

**Costs:**
- Slower (re-parsing on failure)
- Complex control flow
- Exponential worst-case (if many nested choices)

**Preferred approach:** Refactor grammar to LL(1) → no backtracking needed.

### Building AST Nodes: The Propagation Pattern

**Key insight:** Each parse function returns an AST node.

**Pattern:**
1. **Parse components** (call other parse functions)
2. **Collect results** (each returns an AST node)
3. **Construct parent node** (combine children)
4. **Return parent** (propagate up call stack)

**Example: Binary Operator**

```python
def parse_term(self):
    # 1. Parse left operand
    left = self.parse_factor()  # Returns ASTNode
    
    # 2. Parse operator and right operands (loop for left-assoc)
    while self.match(STAR) or self.match(SLASH):
        op = self.current_token.value
        line, col = self.current_token.line, self.current_token.col
        self.advance()
        
        # 3. Parse right operand
        right = self.parse_factor()  # Returns ASTNode
        
        # 4. Build parent node
        left = BinaryOp(op, left, right, line, col)
        # Note: Reassigning 'left' creates left-associative tree
    
    # 5. Return result (propagates up)
    return left
```

**Call stack = implicit tree:**
```
parse_expr()
  returns BinaryOp(+, ...)
    ├─ parse_term() returns IntLiteral(3)
    └─ parse_term() returns BinaryOp(*, ...)
         ├─ parse_factor() returns IntLiteral(4)
         └─ parse_factor() returns IntLiteral(5)
```

**Each function builds its node and returns it. Parent function receives child nodes and wraps them.**

### Error Handling: When Alternatives Fail

**Scenario:** All alternatives in choice fail.

**Example:**
```python
def parse_factor(self):
    if self.match(INT):
        # ...
    elif self.match(ID):
        # ...
    elif self.match(LPAREN):
        # ...
    else:
        # None matched!
        self.error("Expected factor (INT, ID, or '(')")
```

**What happens:**
1. Parser raises `ParseError` with message and location
2. Error propagates up call stack (no catch)
3. Parsing stops
4. User sees: `ParseError: Expected factor at line 1, col 5`

**Better error messages:**
```python
def error(self, message):
    context = self.get_context()  # Show nearby tokens
    raise ParseError(
        f"{message}\n"
        f"  at line {self.current_token.line}, col {self.current_token.col}\n"
        f"  near: {context}\n"
        f"  got: {self.current_token.type}"
    )
```

**Example output:**
```
ParseError: Expected factor (INT, ID, or '(')
  at line 2, col 10
  near: ... x + * 5
               ^
  got: STAR
```

**Helps user understand:** Where error occurred, what was expected, what was found.

## Insights

### Grammar is the Blueprint, Code is the Construction

The mechanical translation from grammar to code is beautiful in its simplicity. **There are no special cases.** Every pattern maps directly:
- Choice → if/elif
- Sequence → sequential calls
- Repetition → while loop
- Recursion → function call

**Like chess opening theory:** Once you know the patterns, you can apply them mechanically.

### Call Stack IS the Parse Tree

The parser doesn't explicitly build a "parse tree" during execution—**the call stack is the tree**. Each function call is a node; returning is moving back up.

The AST we build is a **materialized subset** of this tree (only semantic nodes, not all grammar productions).

### Left-Associativity via Reassignment

The pattern `left = BinaryOp(op, left, right)` in a loop is elegant:
- First iteration: `left = (a op b)`
- Second iteration: `left = ((a op b) op c)`
- Third iteration: `left = (((a op b) op c) op d)`

**Builds left-associative tree without explicit recursion or stack manipulation.**

### Source Location Propagation is Critical

Every AST node construction captures `line, col` from current token. This small overhead pays huge dividends:
- Error messages pinpoint exact location
- Debugging shows where constructs originated
- IDE features (jump to definition) become possible

**Never skimp on location tracking.**

### Backtracking is Usually Avoidable

Most production parsers don't use backtracking because:
1. **Grammar can be refactored** to LL(1) or LL(k)
2. **Backtracking is slow** (re-parsing on failure)
3. **Error messages suffer** (which parse attempt failed?)

**When you think you need backtracking, first try left-factoring.**

## Token Format Unification (Bonus Work!)

### The Problem

Week 4 (lexing) and Week 5 (parsing) used **incompatible token formats**:

| Aspect | Week 4 Lexer | Week 5 Parser |
|--------|--------------|---------------|
| Token type | `TokenType.NUMBER` (enum) | `"INT"` (string constant) |
| Token class | `@dataclass` with type, value, lexeme, line, column | Simple class with type, value, line, col |
| Value field | Parsed value for literals, None for operators | Mixed usage |

This required an **adapter pattern** to convert between formats - unnecessary complexity!

### The Solution

Created **unified token format** in `examples/token_types.py`:

```python
from enum import Enum, auto
from dataclasses import dataclass

class TokenType(Enum):
    NUMBER = auto()
    IDENTIFIER = auto()
    PLUS = auto()
    # ... etc
    
@dataclass
class Token:
    type: TokenType      # Enum for type safety
    value: Any           # Parsed value (int for NUMBER, None for ops)
    lexeme: str          # Original text from source
    line: int            # 1-based line number
    column: int          # 1-based column number
```

**Design decisions:**
- Enum for type safety and IDE autocomplete
- Both `value` (parsed) and `lexeme` (original text) 
- Source location for error messages
- Extensible (future tokens added to enum)

### Benefits

**1. No More Adapters**
- Lexer produces `Token` → Parser consumes same `Token`
- Clean interface, no conversion code
- Like Unix pipes with standardized formats

**2. Type Safety**
- Enum prevents typos (`TokenType.PLSU` caught by IDE)
- String constants error silently

**3. Single Source of Truth**
- All phases import `from token_types import Token, TokenType`
- Changes propagate everywhere
- No version skew between phases

**4. Forward Compatibility**
- Weeks 6-12 (semantics, IR, codegen) all use same tokens
- Add new token types in one place
- No refactoring needed for each phase

### The Real Lesson

**The adapter existed only because we designed phases in isolation.**

In a real compiler:
1. **Define interfaces FIRST** (token format, AST node types, IR format)
2. Put them in `common/` or `shared/` directory  
3. All phases import and use

**Don't bolt together incompatible systems - design the contracts up front.**

**AoC parallel:** Standardized input parsing lets you focus on the algorithm, not format juggling.

**Chess parallel:** Board representation agreed upon from the start - move generation and evaluation use it natively, no conversion.

## Token Format Unification (Architectural Cleanup)

After implementing the parser, discovered that Week 4 and Week 5 used **incompatible token formats**:

### The Fix

Created **unified token format** in `examples/token_types.py`:
```python
from enum import Enum, auto

from typing import Any

class TokenType(Enum):
    # Literals
    NUMBER = auto()
    IDENTIFIER = auto()
    # ... all token types for ALL phases
    
@dataclass
class Token:
    type: TokenType
    value: Any        # Parsed value (42 for NUMBER, None for operators)
    lexeme: str       # Original text ("42")
    line: int         # 1-based line number
    column: int       # 1-based column number
```

The parentheses test fails because Week 4 lexer doesn't support `(` and `)` yet - not a bug, just incomplete. This shows **incremental development**: each week adds features while maintaining compatibility.

### Lessons Learned

**Design interfaces FIRST, then implement phases:**
- Token format is a **contract** between lexer and parser
- Define it once in a shared module
- All phases import from single source of truth
- No adapters needed!

**Chess engine parallel:** Board representation is the contract between move generation and search. Pick one format, stick with it.

**Key insight:** Adapters exist because we designed in isolation. With proper architecture, the pieces fit together naturally.
