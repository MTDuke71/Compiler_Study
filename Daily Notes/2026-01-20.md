## Session Notes

### What Are Regular Languages?

**Definition:** A regular language is one that can be recognized by a **finite automaton** (a state machine with finite states).

**Equivalently:** Regular languages are those that can be described by:
- Regular expressions (regex)
- Finite automata (DFA/NFA)
- Right-linear grammars

**The fundamental insight:** All three formalisms have the **same expressive power** - they recognize exactly the same set of languages.

**Chess Analogy:** Like different notations for the same game. Algebraic notation (e4), long algebraic (e2-e4), coordinate notation, descriptive notation - all describe the same moves. Regular expressions and finite automata are different notations for the same computational concept.

### What Makes a Language Regular?

A language is regular if you can recognize it with a **finite state machine** that has:
- Finite number of states
- No stack or memory (except current state)
- Deterministic or nondeterministic transitions

**What Regular Languages CAN Express:**
- ✅ Keywords (`if`, `while`, `return`)
- ✅ Identifiers (`[a-zA-Z_][a-zA-Z0-9_]*`)
- ✅ Numbers (`[0-9]+`, `0x[0-9A-Fa-f]+`)
- ✅ Simple operators (`+`, `-`, `*`, `/`, `>=`, `==`)
- ✅ Single-line comments (`//.*`)
- ✅ Strings (without nested quotes)

**What Regular Languages CANNOT Express:**
- ❌ Balanced parentheses (`((()))`)
- ❌ Nested block comments (`/* /* */ */`)
- ❌ Matching HTML tags (`<div>...</div>`)
- ❌ Palindromes (`abccba`)
- ❌ Equal numbers of a's and b's (`aabb`, `aaabbb`)

**Why not?** These all require **counting** or **memory** of unbounded depth. A finite automaton can't count arbitrarily high - it only has finite states.

### The Counting Problem

**Example:** Balanced parentheses `((()))`

To recognize this, you need to:
1. Count opening `(`
2. Count closing `)`
3. Verify they match

But with finite states, you can only count up to the number of states you have. For arbitrary nesting depth, you'd need infinite states.

**AoC Analogy:** Like tracking bracket depth in parsing puzzles. A finite state machine is like having only 10 fingers to count on - you can count to 10, but not arbitrarily high. For unlimited counting, you need a stack (context-free grammar territory).

### Finite Automata: DFA and NFA

#### DFA (Deterministic Finite Automaton)

**Properties:**
- Exactly **one** transition per (state, input) pair
- No ambiguity about next state
- Fast execution: O(n) where n = input length
- Larger size (more states than NFA)

**Example:** Recognizing `>=` or `>`

```
States: S0 (start), S1 (saw >), S2 (saw >=)

Transitions:
  S0 --'>'-->  S1 (accepting: GT)
  S1 --'='-->  S2 (accepting: GTE)
  S1 --other-> ERROR
  S2 --any-->  ERROR
```

**Trace on input `>=`:**
```
Position | Input | State | Accepting?
---------|-------|-------|------------
   0     |   >   |  S1   |  YES (GT)
   1     |   =   |  S2   |  YES (GTE)
   2     |  EOF  |  --   |  Return GTE
```

**Why O(n)?** Each input character causes exactly one state transition (array lookup). Process n characters → n transitions → O(n).

#### NFA (Nondeterministic Finite Automaton)

**Properties:**
- Multiple transitions possible for (state, input) pair
- ε-transitions (move without consuming input)
- Smaller size (fewer states than DFA)
- Slower execution (must track multiple states)

**Example:** Recognizing `a*b` (zero or more a's, then b)

```
States: S0 (start), S1 (saw a), S2 (saw b)

Transitions:
  S0 --'a'-->  S1
  S0 --ε---->  S1  (epsilon: skip a's)
  S1 --'a'-->  S1  (loop on a)
  S1 --'b'-->  S2  (accepting)
```

**Trace on input `aab`:**
```
Step | Input | Active States
-----|-------|---------------
  0  |  a    | {S0, S1}  (epsilon closure)
  1  |  a    | {S1}      (self-loop on a)
  2  |  b    | {S2}      (accepting)
```

NFA can be in **multiple states simultaneously**. Must track all possibilities.

### The Power Equivalence: NFA ≡ DFA ≡ Regex

**Theorem:** For any regular language:
- There exists a regex describing it
- There exists an NFA recognizing it
- There exists a DFA recognizing it

**And they all recognize exactly the same languages.**

**The pipeline:**
```
Regex --[Thompson's Construction]--> NFA --[Subset Construction]--> DFA
```

### Thompson's Construction: Regex → NFA

**Algorithm:** Convert each regex operator to NFA fragment, compose them.

**Basic patterns:**

**1. Single character `a`:**
```
[S0] --'a'--> [S1]
```

**2. Concatenation `ab`:**
```
[S0] --'a'--> [S1] --'b'--> [S2]
```

**3. Alternation `a|b`:**
```
       --'a'--> [S1] ---
      /                  ε
[S0] ε                    --> [S3]
      \                  ε
       --'b'--> [S2] ---
```

**4. Kleene star `a*`:**
```
    ----------ε-----------
   |                      |
   v                      |
[S0] --ε--> [S1] --'a'--> [S2] --ε--> [S3]
   |                                   ^
   -----------ε------------------------
```

**Chess Analogy:** Like move generation. Each piece type has a pattern (rook slides in lines, bishop in diagonals). Thompson's construction is like combining piece movement patterns into a complete position evaluator.

### Subset Construction: NFA → DFA

**Problem:** NFA can be in multiple states simultaneously. DFA must be in exactly one state.

**Solution:** Each DFA state represents a **set of NFA states**.

**Algorithm:**
1. Start with ε-closure of NFA start state
2. For each symbol, compute where all active states could transition
3. Create new DFA state for each unique set of NFA states
4. Repeat until all DFA states explored

**Example:** NFA for `a*b`

**NFA states:** {0, 1, 2}

**DFA construction:**
```
DFA state A = ε-closure({0}) = {0, 1}  (can skip to S1 via ε)
  On 'a': {1} (self-loop)
  On 'b': {2} (accepting)

DFA state B = {1}
  On 'a': {1} (self-loop) = state B
  On 'b': {2} (accepting) = state C

DFA state C = {2} (accepting)
  (no transitions - done)
```

**Resulting DFA:**
```
[A] --'a'--> [B] --'a'--> [B]
 |            |
 'b'         'b'
 |            |
 v            v
[C]          [C]  (accepting)
```

**Cost:** NFA with n states → DFA with up to 2ⁿ states (every subset is a potential DFA state).

**In practice:** Most real lexer patterns produce reasonable-sized DFAs. The exponential blowup is rare.

### Why DFA Runs in O(n) Time

**Key insight:** No backtracking, no choices, no ambiguity.

```c
int state = start_state;
for (each character c in input) {
    state = transition_table[state][c];  // O(1) array lookup
    if (state == ERROR) break;
}
return accepting_states[state];  // O(1) check
```

**Complexity:**
- n characters
- O(1) per character (array lookup)
- Total: O(n)

**Compare to backtracking regex engines (PCRE, Python re):**
- Worst case: O(2ⁿ) due to backtracking
- Pattern `(a+)+b` on input `aaaa...aaa` (no b) explodes exponentially

**AoC Analogy:** Like the difference between:
- **Linear scan:** Check each element once (O(n)) - like DFA
- **Recursive exploration:** Try all combinations (O(2ⁿ)) - like backtracking regex

### Why Nested Comments Aren't Regular

**Pattern:** `/* ... /* ... */ ... */`

**Problem:** Need to track nesting depth.

```
Input: /* outer /* inner */ still in outer */
              ^      ^
            depth=2 depth=1
```

**Finite automaton can't do this** because:
- Depth can be arbitrarily deep
- Would need one state per depth level
- But "arbitrarily deep" means **infinite states**
- Contradiction: automaton must be **finite**

**Formal proof (Pumping Lemma):** If nested comments were regular, then for string `/*ⁿ*/ⁿ` (n open comments, n close comments), we could "pump" (repeat) a substring and stay in the language. But we can't - adding more `/*` without matching `*/` breaks the balance. Therefore, not regular.

**Solution:** Need a **pushdown automaton** (finite automaton + stack). This recognizes **context-free languages**, which is what parsers handle.

### Practical Implications for Lexers

**What lexers can do:** Recognize regular patterns (keywords, identifiers, numbers, operators)

**What lexers cannot do:** 
- Balanced parentheses → Parser handles with grammar
- Nested comments → Either disallow (like C), or handle specially in lexer with counter
- Context-dependent tokens → Semantic analysis handles

**Design consequence:** This is **why lexing and parsing are separate phases**. Lexers handle regular patterns (cheap, O(n)). Parsers handle context-free patterns (more expensive, still polynomial).

### DFA State Minimization

After subset construction, DFA may have redundant states.

**Minimization algorithm:**
1. Partition states into accepting/non-accepting
2. Refine partitions: states are equivalent if they transition to equivalent states on all inputs
3. Merge equivalent states

**Result:** Minimal DFA (fewest states possible) for the language.

**Benefit:** Smaller tables, better cache performance, faster execution.

## Insights

1. **Regular languages are exactly those recognizable by finite state machines** - Three equivalent formalisms (regex, NFA, DFA) with same power.

2. **The limitation is counting** - Can't count arbitrarily high with finite states. This is why nested structures aren't regular.

3. **NFA → DFA tradeoff is space for time** - NFA: compact but slow. DFA: larger but O(n) guaranteed.

4. **Maximal munch emerges naturally from DFA execution** - Keep going until stuck, return last accepting state. No special logic needed.

5. **ε-transitions add convenience, not power** - NFAs with/without ε have same expressive power, but ε-NFAs are easier to construct from regex.

6. **Subset construction can be exponential, but rarely is** - Theoretical 2ⁿ blowup, practical lexer patterns stay reasonable.

7. **This theory explains why lexers are fast** - DFA execution is just array lookups in a loop. Simple → fast.
