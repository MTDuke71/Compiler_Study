## Lectures Documented

### [Lecture 18: Parsing Intro](../Stanford/lecture-18-parsing-intro.md) – The Problem

**Core insight:** Regular languages are mathematically insufficient for nested structures.

- **The limitation:** Finite automata can only count modulo k (pigeonhole principle)
- **Why it matters:** Balanced parentheses, nested expressions, nested if/else require arbitrary counting
- **The solution:** Context-free languages (next level up Chomsky hierarchy)
- **Parse trees make nesting explicit:** Transform flat token stream → hierarchical structure
- **Separation of concerns:** Lexer uses regex (regular), parser uses CFG (context-free)

**Key analogy:** Like chess pieces (lexer) vs. legal game positions (parser)—different layers of complexity.

### [Lecture 19: Context-Free Grammars](../Stanford/lecture-19-context-free-grammars.md) – The Specification

**Core insight:** CFGs are the formal notation for describing recursive language structure.

- **Four components:** Terminals (tokens), non-terminals (categories), start symbol, productions (rules)
- **Example:** Balanced parentheses: $S \to (S) \mid \epsilon$
- **Derivations:** Sequences of production applications (mathematical view)
- **Parse trees:** Graphical representation of derivations (implementation view)
- **Key principle:** Multiple derivations can produce the same parse tree

**Test coverage insight:** Simple test cases (50-100) for basic languages; production compilers need thousands to verify all interactions work.

### [Lecture 19b: Implementation Gap](../Stanford/lecture-19b-cfg-implementation-intro.md) – The Reality Check

**Core insight:** CFGs specify membership testing (yes/no), but compilers need much more.

- **Three required capabilities:** Parse tree construction, error handling, efficiency
- **Grammar form matters:** Tools are sensitive to how grammars are written (left-recursion, normal forms)
- **Why it differs from regex:** CFGs more rigid than lexical tools; automatic normalization less common
- **Grammar transformation is common:** Rewrite to match tool constraints (like optimization is common in code)

**Bridge concept:** Theory tells us *what* is valid; algorithms tell us *how* to parse efficiently.

### [Lecture 20: Derivations and Parse Trees](../Stanford/lecture-20-derivations-parse-trees.md) – The Implementation

**Core insight:** Parse trees encode structure and meaning; derivation order doesn't matter.

- **Leftmost derivation:** Always expand the leftmost non-terminal (deterministic)
- **Rightmost derivation:** Always expand the rightmost non-terminal (deterministic)
- **Critical insight:** Both build the same tree; only construction order differs
- **Tree structure encodes precedence:** Lower precedence operators appear higher in tree
- **Why it matters for parsing:** LL parsers use leftmost; LR parsers use rightmost

**Implementation perspective:** Like different strategies to build the same house—order of construction doesn't affect final structure.

### [Lecture 21: Ambiguity](../Stanford/lecture-21-ambiguity.md) – The Problem That Breaks Everything

**Core insight:** Ambiguous grammars are catastrophic—same program has multiple possible meanings.

**Part 1 – The Problem:**
- **Definition:** Multiple parse trees for the same string
- **Concrete example:** `id * id + id` has two trees (different precedence)
- **Dangling else:** Without rules, `else` could match inner or outer `if`
- **Why bad:** Leaves program meaning up to compiler chance

**Part 2 – Two Solutions:**

1. **Grammar rewriting (explicit):**
   - Stratification for operators: E (low precedence) → E + T → T * F → F (high precedence)
   - Matched/unmatched for if-else: Partition statements to force correct associations
   - **Advantage:** Behavior explicit in grammar
   - **Disadvantage:** Complex, hard to maintain

2. **Precedence declarations (implicit):**
   - Keep natural ambiguous grammar
   - Add `%left`, `%right`, `%nonassoc` declarations
   - Order determines precedence (later = higher)
   - **Advantage:** Readable grammars, pragmatic
   - **Disadvantage:** Implicit, tool-specific, requires testing

**Real-world practice:** Production compilers use declarations because pragmatism wins over theory.

### [Lecture 21b: Precedence Declarations](../Stanford/lecture-21b-precedence-declarations.md) – The Pragmatic Approach

**Core insight:** No automatic algorithm converts ambiguous → unambiguous grammars (undecidable). Must choose pragmatism.

- **The caution:** Declarations are heuristics that resolve parsing conflicts, not true semantic understanding
- **Testing required:** Verify declarations work correctly (like perft testing in chess engines)
- **Tool-specific:** Different tools interpret declarations differently
- **Real-world:** Most compilers (GCC, Clang, Python) use declarations

**Historical note:** Perfect grammar structure vs. maintainable grammar—production compilers choose maintainability.

### [Lecture 22: Error Handling](../Stanford/lecture-22-error-handling.md) – The Other Job

**Core insight:** Compilers do two jobs: translate valid programs AND help fix invalid ones. Error handling strategy depends on compilation speed.

**Four error types:**
1. Lexical (invalid characters) → lexer detects
2. Syntax (invalid token order) → parser detects
3. Semantic (type mismatch) → analyzer detects
4. Logical (bugs) → testing/users detect

**Three recovery strategies:**

1. **Panic mode (widely used):**
   - Skip tokens until synchronizing token found (`;`, `}`, statement keywords)
   - Resume parsing from there
   - Works because landmarks are unambiguous

2. **Error productions (pragmatic):**
   - Add grammar rules for common mistakes
   - Treat them as valid (with warnings)
   - Trade-off: readability vs. complexity

3. **Auto-correction (historical):**
   - Try to fix mistakes automatically
   - Was useful in 1970s (slow recompilation, full-day turnaround)
   - PL/C example: compile anything, report many errors
   - Obsolete today: fast recompilation, users fix first error and retry

**Context shift:** Modern philosophy is *accuracy over volume*. First error is most trusted; fix it and recompile (fast).

## Key Insights Across All Lectures

### 1. **Layered Complexity Requires Different Tools**

[[Z0007-chomsky-hierarchy]] Chomsky hierarchy in practice:
- **Regular languages:** Lexing (flat tokens)
- **Context-free:** Parsing (recursive structure)
- **Context-sensitive:** Semantics (constraints)

Each layer needs appropriate formalism. Can't force all levels into one.

### 2. **Theory vs. Practice Gap**

- **Theory says:** Write unambiguous grammars (explicit)
- **Practice does:** Keep natural grammars + declarations (pragmatic)
- **Why:** Maintainability, development speed, tooling support

Same gap as in optimization: theoretical optimality often loses to practical engineering.

### 3. **Testing is Non-Negotiable**

Whether grammar rewriting or precedence declarations:
- **Simple languages:** 50-100 test cases
- **Complex languages:** Thousands of test cases
- **Production compilers:** 10,000+ parser tests

Like chess perft testing—systematic verification proves correctness.

### 4. **Historical Context Shapes Design**

Slow recompilation (1970s) → aggressive error recovery (find many errors in one pass)

Fast recompilation (today) → accurate first error + quick retry

Same infrastructure, different optimization target based on constraints.

### 5. **Parsing is a Solved Problem**

Lectures 18-22 define the *problem space*. Next lectures will present specific algorithms (LL, LR, recursive descent) that solve it. The theory is settled; only implementation strategies vary.

## Reflection

This week's lectures established that **parsing is a solved problem** with well-understood formal foundations and pragmatic engineering solutions. The theory (CFGs, ambiguity, error recovery) has been settled for decades. What varies is *how* we implement it—and that depends on specific language, tool, and workflow constraints.

The key insight: **theory provides the space; engineering fills it wisely**. Stratified grammars are theoretically elegant but too complex; precedence declarations are pragmatically useful. Both solve the same problem; context determines the right choice.
