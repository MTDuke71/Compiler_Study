## Session Notes

### The Boundary
- **Lexing** is about *chunks*: characters → tokens
- **Parsing** is about *shape*: tokens → structure (AST)
- They exist as separate phases because each has different rules, tools, and failure modes

### What Each Phase Does

#### Lexing
- **Input:** source text (characters)
- **Output:** token stream (plus source locations)
- **Typical errors:** unknown character, malformed number/string, unterminated string/comment

#### Parsing
- **Input:** token stream
- **Output:** tree (parse tree or AST)
- **Typical errors:** unexpected token, missing delimiter, ambiguous or unsupported syntax

### Worked Example: `x = 3 + 4 * 5`

**Tokens (after lexing):**
```
IDENT(x)  EQUALS  INT(3)  PLUS  INT(4)  STAR  INT(5)
```

**Structure (after parsing):**
```
Assign(
  name = "x",
  value = Add(Int(3), Mul(Int(4), Int(5)))
)
```

## Insights

Each compilation phase trades compactness for precision — what was implicit becomes explicit:
- Source is compact but ambiguous (precedence is implied)
- Tokens make boundaries explicit (where symbols start/end)
- AST makes structure explicit (precedence encoded in tree nesting)

Each representation is optimized for its consumer: source → humans, tokens → parser, AST → semantic analyzer, IR → optimizer, machine code → CPU.  See [[Z0005-compiler-phases]]

## Questions Raised

Source locations (line/column) must be tracked through every compiler phase, not just lexing — they're copied to AST nodes, used in semantic errors, preserved for debuggers, and emitted in debug metadata.
