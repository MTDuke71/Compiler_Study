## Session Notes

### Lexer Generators Comparison

Completed comprehensive analysis of hand-written vs. generated lexers. The choice isn't about one being "better" - it's context-dependent, much like choosing evaluation complexity vs. search depth in chess engines.

**Hand-Written Lexers:**
- Full control over error messages and recovery
- Easier to debug (step through human-readable code)
- Better for tight parser integration (can add state, lookups)
- Typical in production compilers (GCC, Clang, Rust, Go)
- ~200-500 lines of maintainable code

**Generated Lexers (Flex):**
- Easier to maintain (change spec, regenerate)
- Specification IS the documentation
- Automatic DFA optimization (subset construction, minimization)
- Harder to customize error handling
- ~10 lines of spec → ~2000 lines of generated code

**Key finding:** Maintainability favors generated despite larger code size. The specification is clearer than scattered state machine logic.

### Performance Measurements

Surprising result: **Performance difference is negligible** in practice.

Both execute DFAs in O(n) time. Typical throughput: 100-150 MB/s on modern hardware.

More importantly: **Lexing is only 5-10% of compile time**. Even a 2x faster lexer only speeds up compilation by ~5%. This is the AoC lesson applied - measure before optimizing. The real bottlenecks are semantic analysis (15-25%) and optimization (40-60%).

**When lexer performance matters:**
- IDE use (re-lex on every keystroke)
- Huge files (millions of lines)
- Lexer IS the application (JSON parser, log processor)

### Real-World Integration

Examined two integration patterns:

**Pull Model (most common):**
```c
Token next_token(Lexer* lexer);
Token peek_token(Lexer* lexer, int lookahead);
```
Parser controls flow, pulling tokens on demand. Simple and flexible.

**Push Model:**
```c
void tokenize(Lexer* lexer, TokenStream* stream);
```
Lexer produces all tokens upfront. Enables parallel tokenization but requires memory for entire stream.

**Complication:** Some languages require parser feedback. Example: C typedef - the lexer can't know if `mytype` is a type name without symbol table info. This is why C compilers use hand-written lexers (easy to add `is_typedef()` checks).

## Insights

1. **Generated code can be more maintainable than hand-written code** - This initially seemed backwards (2000 lines vs. 200), but the *specification* is what you maintain, not the generated output. Like how you maintain training data/architecture for a neural net, not the weights directly.

2. **Performance usually doesn't matter** - The AoC lesson applies perfectly here. Lexer optimization is rarely worth the effort because it's only 5-10% of compile time. Better to focus on data flow analysis or optimization passes.

3. **Production compilers favor control over convenience** - All major language compilers (C, C++, Rust, Go, Python) use hand-written lexers. They're willing to pay the maintenance cost for better error messages and parser integration. Research compilers use generators (focus on other phases).

4. **Simple algorithms scale to production** - DFA execution is trivial to understand, yet it powers every production lexer. No fancy data structures needed. The complexity is in *constructing* the DFA (regex → NFA → DFA), not running it.

5. **Tradeoffs are everywhere** - Every design choice has costs. Hand-written = control but maintenance burden. Generated = easy changes but limited customization. Table-driven DFA = predictable but larger code. Direct-coded DFA = smaller but less maintainable. Context determines the right choice.

6. **Error recovery quality matters for UX** - Developers run compilers on broken code constantly. A lexer that reports "unexpected character" and stops is technically correct but poor UX. A lexer that recovers intelligently (skip to next valid token, assume missing quote) enables reporting multiple errors per run.

## Questions Raised

1. **Could you combine lexer and parser into one phase?** 
   - Yes (scanner-less parsing, some PEG parsers do this)
   - But loses separation of concerns, harder to maintain
   - Why do most compilers keep them separate?

2. **How do IDEs handle incremental lexing?**
   - Re-lex only changed region
   - Requires saving state at every line (for resumption)
   - What's the state overhead?

3. **What about languages with context-sensitive lexing?**
   - Python's INDENT/DEDENT tokens
   - C's typedef disambiguation
   - How much state does lexer need to maintain?

4. **Why not use more powerful parsing at lexer level?**
   - Could use CFG instead of regex
   - But O(n³) worst case vs. O(n) guaranteed
   - When is extra power worth the cost?

5. **How do lexer generators compare across languages?**
   - Flex (C/C++), JFlex (Java), Alex (Haskell), re2c (C)
   - Do they make the same tradeoffs?
   - Is table-driven vs. direct-coded a fundamental split?
