## Session Notes

### What Are Invariants?

**Definition:** An invariant is a property that must remain true throughout a transformation or across all states in a process.

In compilers, invariants are:
- **Guarantees** that every phase must preserve
- **Contracts** between compiler phases
- **Assumptions** that downstream code can rely on
- **Debugging checkpoints** when things go wrong

**Why They Matter:**

1. **Safety**: Transformations that violate invariants produce incorrect programs
2. **Modularity**: Each phase can assume invariants from prior phases without re-verification
3. **Debugging**: When something breaks, check which invariant was violated
4. **Optimization**: Many optimizations rely on specific invariants holding

**Example:**
- The parser can assume tokens are well-formed (lexer's invariant)
- The optimizer can assume types are consistent (semantic analyzer's invariant)
- Code generation can assume control flow is explicit (IR's invariant)

### The Master Invariant: Meaning Preservation

**The Fundamental Rule:** The program's **observable behavior** must not change.

Observable behavior includes:
- Input/output operations
- Return values
- Side effects (memory writes, exceptions)
- Termination vs. non-termination

**NOT included** (implementation details):
- Execution time (performance improvements are allowed!)
- Memory layout (as long as behavior is same)
- Instruction order (if semantics are preserved)
- Register allocation choices

**This is the invariant that all other invariants serve to uphold.**

### 5 Critical Compiler Invariants

#### 1. **Type Safety** (after semantic analysis)
**Property:** Every expression has a consistent type; operations receive arguments of correct types.

**Requirements:**
- `int + int` → `int`
- `string + string` → `string`
- NO `int + string` (unless language allows with explicit conversion)

**Violation Example:**
```
// WRONG: Changing types during optimization
Original: int x = 5 + 3;         // int + int → int
Optimized: float x = 5.0 + 3.0;  // VIOLATES type invariant!
```

#### 2. **Well-Formedness**
**Property:** Each IR is structurally valid for its representation.

**Phase-specific requirements:**
- **Tokens**: Each has type, value, position
- **AST**: Nodes have correct number and type of children
- **CFG**: Valid edges, no dangling jumps
- **SSA**: Single assignment property maintained

**Violation Example:**
```
// WRONG: Creating a CFG block with no exit
Block {
  x = 5;
  y = 10;
  // No jump, return, or fall-through!
}
```

#### 3. **Scope Validity**
**Property:** Variables are defined before use; names resolve correctly; scopes are properly nested.

**Requirements:**
- All identifiers are declared
- Use-before-definition is caught
- Shadowing rules are enforced

**Violation Example:**
```
// WRONG: Reordering moves use before definition
Original:          Optimized:
  int x = 5;         print(x);  // BUG: x used before defined!
  print(x);          int x = 5;
```

#### 4. **Control Flow Reachability**
**Property:** All code is either reachable or explicitly dead; every function path ends properly.

**Requirements:**
- Every block is reachable from entry (or marked dead)
- All non-void function paths end in return/throw
- No infinite loops without side effects (unless intended)

**Violation Example:**
```
// WRONG: Creating unreachable code unintentionally
if (true) {
  return 1;
}
// This block is unreachable but not removed
Block {  // Dangling block with no incoming edges
  x = 5;
}
```

#### 5. **Data Flow Consistency**
**Property:** Every variable use has a corresponding definition; definitions dominate uses.

**Requirements:**
- No use of uninitialized variables
- In SSA: definitions dominate all uses
- Use-def chains are valid

**Violation Example:**
```
// WRONG: Removing definition but keeping uses
Original:              Optimized:
  x = 5;                 // [removed x = 5 as "dead"]
  if (condition) {       if (condition) {
    print(x);              print(x);  // BUG: x undefined!
  }                      }
```

### How to Verify Invariants Are Maintained

#### 1. **Static Verification** (at compile time)
- **Type checking**: Proves type safety
- **Dataflow analysis**: Proves variables defined before use
- **CFG validation**: Proves control flow is valid
- **SSA validation**: Proves single assignment property

#### 2. **Dynamic Verification** (runtime checks)
- **Assertions in compiler code**: `assert(x != nullptr)`
- **IR verification passes**: Run after each transformation
- **Test suites**: Known-good programs that should compile
- **Differential testing**: Compare with other compilers/interpreters

#### 3. **Common Verification Techniques**

**Assertion Checks:**
```cpp
void addEdge(Block* from, Block* to) {
    assert(from != nullptr);
    assert(to != nullptr);
    assert(from->cfg == to->cfg);  // Same CFG
    from->successors.push_back(to);
}
```

**Verification Passes:**
```
Pipeline:
  Lexing → [Verify tokens] →
  Parsing → [Verify AST] →
  Semantics → [Verify types/scopes] →
  IR → [Verify CFG/SSA] →
  Optimization → [Verify equivalence] →
  Codegen → [Verify instructions]
```

**Property-Based Testing:**
- Generate random valid programs
- Verify invariants hold after each phase
- Compare output with reference implementation

#### 4. **Real-World Example: LLVM Verifier**
LLVM has a built-in verifier that checks:
- SSA form is valid
- Types are consistent
- CFG is well-formed
- Instructions are legal
- Metadata is correct

### How Invariants Enable Safe Optimizations

**Key Insight:** If you know certain properties always hold, you can transform code without rechecking everything.

#### Example 1: Constant Folding
**Relies on:** Type safety, pure computation (no side effects)

```
Before: x = 2 + 3
After:  x = 5

Why safe?
✓ Type safety: int + int → int preserved
✓ No side effects: Addition is pure
✓ Meaning preservation: Same result
```

#### Example 2: Common Subexpression Elimination
**Relies on:** Data flow consistency, no intervening writes

```
Before: a = x + y;
        b = x + y;
        
After:  a = x + y;
        b = a;

Why safe?
✓ x and y not modified between uses
✓ Same types (verified by type safety)
✓ Same result (meaning preserved)
```

#### Example 3: Dead Code Elimination
**Relies on:** Dataflow analysis showing no uses

```
Before: x = 5;  // x is never used
        y = 10;
        
After:  y = 10;

Why safe?
✓ No uses of x (dataflow proved it)
✓ No side effects in assignment
✓ Behavior unchanged (meaning preserved)
```

### When Does an Optimization Violate an Invariant?

An optimization violates an invariant if it:
1. **Changes program output** (violates meaning preservation)
2. **Changes exception behavior** (violates control flow)
3. **Changes termination** (finite → infinite or vice versa)
4. **Reorders side effects** (I/O, memory writes)
5. **Makes defined behavior undefined** (introduces UB)
6. **Violates language semantics** (type rules, evaluation order)

### Safe vs Unsafe Transformation Examples

#### ✅ **SAFE Transformations:**

**1. Constant Folding:**
```
x = 2 + 3  →  x = 5
```
Pure computation, no side effects.

**2. Algebraic Simplification:**
```
x = y * 1  →  x = y
x = y + 0  →  x = y
```
Mathematically equivalent (for integers).

**3. Dead Code Elimination (pure code):**
```
x = 5; /* x never used */  →  [removed]
```
No side effects, no observable impact.

**4. Reordering Independent Statements:**
```
a = 1;     b = 2;
b = 2;  →  a = 1;
```
No dependencies, same result.

#### ❌ **UNSAFE Transformations:**

**1. Removing I/O Operations:**
```
x = read();  /* x never used */  →  [removed]  ❌
```
**Violates:** Meaning preservation (side effect removed!)

**2. Removing Infinite Loops with Side Effects:**
```
while(true) { print("x"); }  →  [removed]  ❌
```
**Violates:** Termination behavior and side effects!

**3. Reordering Floating-Point Operations:**
```
x = (a + b) + c  →  x = a + (b + c)  ❌
```
**Violates:** Floating-point is not associative (rounding differs!)

**4. Hoisting Potentially-Throwing Operations:**
```
if (cond) { x = arr[i]; }  →  x = arr[i]; if (cond) { use(x); }  ❌
```
**Violates:** Exception semantics (throws even when cond is false!)

**5. Eliminating "Dead" Code with Side Effects:**
```
// Original
x = launch_missile();  // x unused
print("done");

// WRONG optimization
print("done");  // Removed missile launch! 💥
```
**Violates:** Side effects must be preserved!

### Phase-Specific Invariants Summary

**Lexing:**
- Every character consumed
- No overlapping tokens
- Position info accurate

**Parsing:**
- Grammar conformance
- Correct precedence/associativity
- Complete AST structure

**Semantic Analysis:**
- All names declared
- Types consistent
- Scopes properly nested
- Variables initialized before use

**IR Translation:**
- Control flow explicit
- All jumps have valid targets
- Storage allocated
- Side effect order preserved

**Optimization:**
- Meaning preservation (critical!)
- Dataflow facts valid
- Cannot optimize away I/O
- Exception semantics preserved

**Code Generation:**
- Calling conventions followed
- All values in registers/memory
- Valid instruction encoding
- Proper alignment

### Recognizing Invariant Violations: A Checklist

When reviewing a transformation, ask:

1. **Does it preserve types?**
   - Check: Do operand types change?

2. **Does it preserve control flow?**
   - Check: Can execution paths change?

3. **Does it preserve data flow?**
   - Check: Do values reach different places?

4. **Does it preserve side effects?**
   - Check: Are I/O operations reordered/removed?

5. **Does it preserve termination?**
   - Check: Can terminating code become infinite (or vice versa)?

6. **Does it preserve exceptions?**
   - Check: Can new exceptions be thrown or caught ones be missed?

If **any** answer is "it might", the transformation needs closer scrutiny!

## Insights

### Key Realizations

1. **Invariants are contracts, not suggestions**
   - Violated invariants = bugs, not warnings
   - Each phase relies on prior phases maintaining their invariants
   - Breaking an invariant can cause cascading failures in later phases

2. **The compiler is only as trustworthy as its invariant maintenance**
   - A compiler that doesn't verify invariants is a "bug generator"
   - Real compilers (LLVM, GCC) have extensive verification passes
   - Adding verification early catches bugs before they propagate

3. **Most optimization bugs come from invariant violations**
   - "This code is dead" ← didn't check for side effects
   - "These operations commute" ← didn't check for floating-point
   - "This value is unused" ← didn't update use-def chains

4. **Invariants enable composability**
   - Add new optimization? Just maintain invariants.
   - Change IR representation? Phases still work if invariants hold.
   - This is why compilers can have hundreds of optimization passes!

### Exercise 2: Safe or Unsafe?

Determine if each transformation is safe, and explain why:

**2.1:** `x = y * 2` → `x = y << 1` (shift instead of multiply)

**Answer:** ✅ **Safe** (for integers)
- Semantically equivalent for integers
- Types preserved
- No side effects
- Faster (performance improvement allowed)

---

**2.2:** `if (x > 0) { print(x); }` → `print(x); if (x <= 0) { crash(); }`

**Answer:** ❌ **Unsafe**
- Changes control flow
- Crashes when original wouldn't
- Violates meaning preservation

---

**2.3:** `a = x + y; b = x + y;` → `a = x + y; b = a;`

**Answer:** ✅ **Safe** (if x, y not modified between)
- Common subexpression elimination
- Semantically equivalent
- No side effects in `x + y`
- Types preserved

---

**2.4:** `x = malloc(100); [x never used]` → `[removed]`

**Answer:** ❌ **Unsafe**
- `malloc` has side effects (memory allocation)
- Could affect program behavior (memory pressure, OOM)
- Should still remove if language allows (implementation detail)
- *Technically safe for observable behavior, but tricky!*

---

**2.5:** `x = 0; x = 5;` → `x = 5;`

**Answer:** ✅ **Safe**
- First assignment is dead (no uses)
- No side effects
- Result is identical
- Dead store elimination

### Exercise 3: Design a Verification Pass

**Task:** Design a verification pass to check that all variables are defined before use.

**Answer:**

```
Algorithm: Check Def-Before-Use Invariant

1. Build control flow graph (CFG)
2. For each basic block:
   a. Track defined variables (set D)
   b. For each statement in block:
      - If variable use: check if variable ∈ D
      - If violation: report error with location
      - If variable definition: add to D
3. For successor blocks:
   - Propagate D (defined variables)
4. Handle phi nodes at joins:
   - Check all incoming paths define the variable
5. Report all violations found

Data structures:
- CFG: Graph of basic blocks
- DefSet: Set of defined variables per block
- UseSet: Set of used variables per block
- WorkList: Blocks to process (dataflow iteration)

Complexity: O(n) where n = number of statements
```

### Exercise 4: Real-World Scenario

**Scenario:** You're adding a new optimization that reorders loop iterations. What invariants must you check?

**Answer:**

**Must Verify:**

1. **Data Dependencies**
   - Check: Do iterations have dependencies?
   - Tool: Dependence analysis
   - Example: `a[i] = a[i-1] + 1` has loop-carried dependency

2. **Side Effect Order**
   - Check: Are there I/O operations?
   - Example: `print(i)` must stay in order

3. **Exception Semantics**
   - Check: Can exceptions be thrown?
   - Example: `arr[i]` might throw out-of-bounds

4. **Termination**
   - Check: Does reordering affect loop condition?
   - Example: Ensure loop still terminates

5. **Memory Model** (for concurrent code)
   - Check: Are there synchronization points?
   - Example: Volatile/atomic operations

**Safe to reorder if:**
- No loop-carried dependencies
- No side effects (pure computation)
- No exceptions (or provably safe)
- Independent iterations

**Common safe case:** Parallel iteration over immutable data with pure function.
