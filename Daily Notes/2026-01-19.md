## Session Notes

### What Is Lexing?

**The Core Abstraction:** Lexing transforms a stream of **characters** into a stream of **tokens**.

- **Input:** `if x > 10 then`
- **Output:** `[IF, IDENT("x"), GT, NUMBER(10), THEN]`

This is the first phase of ambiguity removal: characters are ambiguous (is `>` part of `>=` or standalone?), but tokens are discrete units with clear boundaries.

**Chess Analogy:** Like converting board notation. Moving from "e4" (text) to board position (structured data) to piece placement (internal representation). Each step removes ambiguity and makes the next phase's job easier.

### Why Separate Lexing from Parsing?

**Separation of Concerns:**
1. **Performance:** Lexing is character-by-character; parsing works with higher-level structures
2. **Simplicity:** Parser doesn't care about whitespace or comment handling
3. **Reusability:** Same lexer for different parsing strategies
4. **Modularity:** Can test/optimize each phase independently

**AoC Parallel:** Like parsing input files - first split on delimiters (lexing), then validate structure (parsing). Trying to do both at once creates spaghetti code.

### Lexer Responsibilities

The lexer must:
1. **Recognize token boundaries** (maximal munch: `>=` not `>` and `=`)
2. **Filter noise** (whitespace, comments) while preserving line numbers
3. **Handle keywords** (is `if` an identifier or keyword?)
4. **Maintain position** (line/column for error messages)
5. **Detect lexical errors** (unclosed strings, invalid characters)

**What Must Be Preserved:**
- Token type and value
- Source location (file, line, column)
- Original text (for error reporting)

### How Lexing Removes Ambiguity

**Character Level (Ambiguous):**
- Is this `>` or `>=` or `>>`?
- Does whitespace matter here?
- Is this escape sequence valid?

**Token Level (Unambiguous):**
- `GT` token (greater than)
- Whitespace already filtered
- String validated, escapes processed

The lexer commits to interpretations so the parser doesn't have to.

### Tokens vs. Characters

**Why Characters Aren't Enough:**
- Parser would need to know: "is this sequence of letters a keyword?"
- Error messages would be terrible: "expected THEN at character 47"
- Performance: parser makes many decisions; character-level would be O(n²)

**Why Tokens Are Better:**
- Fixed vocabulary
- O(1) comparison
- Semantic information attached
- Position preserved for errors

**Chess Parallel:** Pieces vs. pixels. You don't evaluate a chess position by analyzing the color values of each square's pixels - you work with "white knight on f3" (tokens). The board image (characters) must first be tokenized into piece positions.

## Insights

1. **Lexing is about commitment:** The lexer makes irreversible decisions (this is `>=`, not `>` followed by `=`) so downstream phases don't have to backtrack.

2. **Whitespace is harder than it looks:** Significant in Python, noise in C, but line numbers matter everywhere. The lexer must track what to keep vs. discard.

3. **Keywords vs. identifiers is contextual:** `if` might be a keyword in most languages, but what about user-defined names? The lexer must know the language's keyword list.

4. **Position tracking is non-negotiable:** Without line/column information, error messages become useless. This is a core invariant.

5. **Maximal munch matters:** When `>=` exists as a token, seeing `>` followed by `=` requires lookahead. The lexer commits to the longest match.
