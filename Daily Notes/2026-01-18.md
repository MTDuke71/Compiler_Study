### Phase 2: Lexical Analysis Algorithm (Lecture 12)

**The complete algorithm for using regex in lexers:**

**Three disambiguation rules:**
1. **Maximal munch:** Always take longest match
2. **Priority ordering:** First-listed pattern wins ties
3. **Error handling:** Catch-all pattern (lowest priority)

**Why these rules:**
- Maximal munch: Mimics human reading (`==` not two `=`)
- Priority: Keywords before identifiers (avoid ambiguity)
- Error pattern: Graceful failure, don't crash

**Example:**
```regex
Keyword    = "if" + "else"     ← Priority 1
Identifier = [a-zA-Z]+         ← Priority 2
Error      = .+                ← Priority 3 (last!)
```

Input `"if"` matches both Keyword and Identifier → Priority 1 wins → Keyword token

**Key Insight:** Specification alone isn't enough; need **execution rules** for ambiguity.

### Phase 3: State Machines (Lecture 13)

**Finite automata = executable model for regular expressions**

**Components:**
- States (finite set)
- Start state (one)
- Accepting states (subset)
- Transitions: (state, input) → next state

**Execution model:**
- Configuration = (current state, input pointer)
- Read character → transition → advance pointer
- Accept if: (1) consumed all input AND (2) in accepting state

**Example automaton for `1*0`:**
```
         +--1--+
         |     |
         v     |
    ( A ) --0--> (( B ))
```

**Properties:**
- Input pointer only advances (no backtracking!)
- Single-pass execution
- O(1) per character

**Key Insight:** Finite automata enable **linear-time lexing** without backtracking.

---

### Phase 4: Nondeterminism (Lecture 14)

**NFAs allow choices during execution**

**Two forms of nondeterminism:**
1. **ε-moves:** Change state without consuming input
2. **Multiple transitions:** Same (state, input) → multiple next states

**Execution model:**
- Track **set of states** simultaneously
- Accept if **any path** reaches accepting state

**Example: Strings ending in `01`:**
```
         +--0--> ( B ) --1--> (( C ))
         |
    ( A ) 
      |  |
      +--0--> ( A )
      +--1--> ( A )
```

**DFA vs NFA tradeoffs:**
- **NFAs:** Small, easy to construct, slow execution (track sets)
- **DFAs:** Large, hard to construct, fast execution (single state)
- **Both:** Recognize exactly the same languages (regular languages)

**Key Insight:** NFAs are **construction tools**, DFAs are **execution tools**.

### Phase 5: Thompson's Construction (Lecture 15)

**Algorithm: Regex → NFA (mechanical, always works)**

**Five patterns (one per regex form):**

**1. ε:**
```
(start) --ε--> ((final))
```

**2. Single char `a`:**
```
(start) --a--> ((final))
```

**3. Concatenation `A·B`:**
```
[NFA(A)] --ε--> [NFA(B)]
```
Connect A's final to B's start with ε

**4. Union `A+B`:**
```
           ε
    +----------> [NFA(A)] --+
    |                       | ε
(start)                 (final)
    |                       ↑
    +-----ε----> [NFA(B)] --+
```
Branch at start, merge at end

**5. Kleene star `A*`:**
```
         ε (skip)
    +-----------------+
    |    ε (repeat)   |
    v   +--------+    v
(start)-ε->[NFA(A)]--ε->(final)
```
Skip for zero, loop for repetition

**Properties:**
- Linear states: O(|regex|)
- Lots of ε-transitions (glue)
- One start, one final (easy composition)
- Proven correct by induction

**Key Insight:** ε-transitions make construction **modular and mechanical**.

---

### Phase 6: Subset Construction (Lecture 16)

**Algorithm: NFA → DFA (eliminate nondeterminism)**

**Core idea:** DFA state = **set of NFA states**

**ε-closure:** All states reachable via ε-transitions
```
ε-closure(s) = {t | s →ε* t}
```

**Subset construction algorithm:**
1. Start: DFA start = ε-closure(NFA start)
2. For each DFA state X and input a:
   - Find NFA states reachable from X on a
   - Compute ε-closure of those states → new DFA state Y
   - Add transition X →a Y
3. DFA accepting: Contains any NFA accepting state

**Example:**
```
NFA states: {A, B, C, D, E}
DFA state 1: {A, B, C}     (ε-closure from A)
DFA state 2: {D, E}        (after reading '1')
```

**Properties:**
- Theoretical size: 2^n states (exponential!)
- Practical size: Often small (lazy construction, only reachable states)
- No ε-transitions in DFA
- Proven equivalent: L(DFA) = L(NFA)

**Key Insight:** Track **all possibilities** in one deterministic state.

---

### Phase 7: Implementation (Lecture 17)

**Algorithm: DFA → Executable code**

**Transition table (2D array):**
```
table[state][input] = next_state
```

**Execution loop:**
```c
state = START_STATE;
i = 0;
while (input[i] != '\0') {
    state = table[state][input[i]];
    i++;
}
return is_accepting[state];
```

**Per character:** 3 operations (lookup, assign, increment)

**Space optimization:** Share duplicate rows via pointers
```c
int* state_table[NUM_STATES];  // Pointers
state_table[S] = transitions_S;
state_table[T] = transitions_TU;  // Shared!
state_table[U] = transitions_TU;  // Shared!
```

**Alternative: Direct NFA implementation**
- Slower (O(S²) per char)
- Smaller tables
- Skip DFA when exponential blowup

**Real tools:** Offer configuration (fast DFA vs compact tables)

**Key Insight:** Table-driven execution is **trivially simple and blazingly fast**.

## Major Insights

### 1. The Magic is Gone (in a Good Way!)

**Before:** Regex seems like magic  
**After:** Complete understanding of implementation pipeline

Every `re.match()` in Python, every lexer in GCC/Clang:
- Compiles regex to NFA (Thompson's)
- Converts NFA to DFA (subset construction)  
- Executes DFA (table lookup)

**No mystery, just well-understood algorithms.**

---

### 2. Multiple Representations Solve Different Problems

**Regex:** Human-friendly specification  
**NFA:** Easy to construct from regex  
**DFA:** Fast to execute  
**Tables:** Embeddable in code

**Each form optimized for its purpose.** Pipeline transforms specification → implementation.

---

### 3. Tradeoffs Are Everywhere

| Aspect | NFA | DFA |
|--------|-----|-----|
| Construction | Easy | Hard |
| Size | Small | Large |
| Execution | Slow | Fast |

**No "best" choice—depends on constraints.**

Real tools let users choose via flags (`-f` for fast, `-Cm` for minimal, etc.)

---

### 4. Theory ↔ Practice Connection

**Theory provides:**
- Correctness guarantees (proven algorithms)
- Complexity bounds (O(n) lexing)
- Equivalence proofs (NFA ≡ DFA ≡ Regex)

**Practice provides:**
- Optimization techniques (row sharing, lazy construction)
- Tool design (Lex, Flex, RE2)
- Real-world tradeoffs

**Both essential!** Theory alone = impractical. Practice alone = buggy.

---

### 5. Simple Loops Are Powerful

**DFA execution:**
```c
while (input[i]) {
    state = table[state][input[i]];
    i++;
}
```

**Three lines.** Processes entire source code.

**Why so fast?**
- No branches (just array access)
- Sequential memory (good cache)
- Predictable (CPU pipelines well)

**Lesson:** Simplest solution often fastest.

## Questions Raised (Resolved!)

1. **Why can't variable names start with digits?**
   - Would create lexical ambiguity (is `123abc` one token or two?)
   - By design: keep numbers and identifiers disjoint for clear lexing

2. **How are missing semicolons detected?**
   - NOT lexer's job! Lexer just produces tokens.
   - Parser's job: expects semicolon after statement (syntax check)

3. **How is `@` in variable name detected?**
   - Error token pattern (lowest priority catch-all)
   - Matches anything not in valid patterns
   - Lexer reports: "Unexpected character '@'"

4. **Does backtracking happen in lexing?**
   - NO for regular languages! (Modern language design)
   - Fortran/PL/I disasters showed why to avoid it
   - DFA = guaranteed single-pass, no backtracking

5. **Lecture 12 says single-pass, Lecture 8 mentions backtracking—contradiction?**
   - NO! Different languages:
     - Regular specs → single-pass (DFA)
     - Context-dependent (Fortran, PL/I) → backtracking needed
   - Modern languages keep lexing regular → DFA works
