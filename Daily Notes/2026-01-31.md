## Key Concepts Covered

### LL(1) Predictive Parsing

**Core insight:** Use lookahead to decide which production to apply without backtracking.

**Key components:**
- **FIRST sets:** What terminals can start a string derived from a nonterminal
- **FOLLOW sets:** What terminals can appear after a nonterminal in a derivation
- **Parsing table:** Maps (nonterminal, lookahead) → production
- **Conflicts:** Multiple entries in same table cell = grammar not LL(1)

**Limitations:**
- Requires left factoring (no common prefixes)
- Cannot handle left recursion
- Less general than LR parsing

### Bottom-Up Parsing Introduction

**Core insight:** Build parse tree from leaves upward by reducing terminals to start symbol (productions run backward).

**Key properties:**
- Traces **rightmost derivation in reverse**
- More general than LL(1) — handles left recursion naturally
- Preferred by parser generators (yacc, bison)

**Shift-reduce mechanism:**
- **Shift:** Read one token onto stack
- **Reduce:** Replace stack top matching production RHS with LHS
- **Vertical bar `|`:** Marks boundary between examined (stack) and unexamined (input) tokens

**Conflicts:**
- **Shift-reduce:** Don't know whether to read more or reduce now (often precedence issues)
- **Reduce-reduce:** Multiple productions could apply (serious grammar problem)

## Insights

### Pattern Recognition Across Parsing Strategies

Both LL and LR parsing share a common structure:
1. **Precomputation phase:** Build tables/sets (FIRST/FOLLOW for LL, states for LR)
2. **Table-driven execution:** Linear-time parsing using precomputed information
3. **Conflict detection:** Some grammars don't fit the method (not LL(1), not LR(k))

Like chess opening books — do the hard analysis once, execute quickly at runtime.

### Why Bottom-Up is More Powerful

LL parsing makes decisions **before** seeing the full context (expanding nonterminals top-down).

LR parsing makes decisions **after** seeing context (reducing once patterns are recognized).

More information → better decisions → accepts more grammars.

### The FOLLOW Set Puzzle

Discovered interesting grammar limitation: In the pedagogical grammar, `*` is NOT in FOLLOW()) because the grammar structure prevents multiplication after closing parenthesis. The grammar can't parse `(int) * int` — after closing `)`, you're back at the E level where only `+` is allowed. This is a **grammar design limitation**, not a FOLLOW set bug.
