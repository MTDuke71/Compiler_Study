## Session Notes

### The Testing Problem: Correctness as Invariants

**Like perft testing in chess engines:** You need checksums to verify correctness.

**Lexer invariants:**
- Every character in input is either part of a token or whitespace
- No gaps in source positions
- No overlapping tokens
- Total input consumed OR error reported

**Test categories:**
1. **Unit tests:** Individual token patterns in isolation
2. **Sequence tests:** Maximal munch verification
3. **Error cases:** Recovery and messages
4. **Position tracking:** Line/column accuracy
5. **Stress tests:** Performance and limits

**Key insight:** Tests should verify ONE thing. Start simple, add complexity incrementally. (AoC lesson applies to testing too.)

### Common Failure Modes (The Real World Intrudes)

**1. Maximal Munch Violations**
- Problem: `>=` becomes `>` followed by `=`
- Fix: Always peek ahead before committing

**2. Position Tracking Errors**
- Problem: Line/column drift from reality
- Causes: Forgetting to increment on `\n`, mixing `\r\n` and `\n`
- Fix: Update position on EVERY character consumed

**3. Unclosed Delimiters**
- Problem: Unterminated string scans to EOF
- Fix: Check for newline/EOF while scanning, error gracefully

**4. Escape Sequence Handling**
- Problem: `\n` stored as two characters instead of newline
- Fix: Process escapes during scanning

**5. Unicode and Character Encoding**
- Problem: Multi-byte UTF-8 treated as separate chars
- Fix: Use language's proper Unicode handling

**6. Numeric Overflow**
- Problem: `99999999999999999999` too large
- Options: Error during lexing, token with flag, arbitrary precision
- Best: Lexer recognizes syntax, semantic analysis checks range

**7. Ambiguous Lexical Rules**
- Problem: Is `if` a keyword or identifier?
- Resolution: Keywords take precedence

**8. Whitespace and Comment Handling**
- Options: Discard, preserve for formatter, include in stream
- Edge cases: Multiple whitespace, EOF without newline, mixed tabs/spaces

**Chess analogy:** These are like illegal move detection—the board state can become invalid, and you need to handle it gracefully.

### Performance Considerations (Measure, Don't Guess)

**What to measure:**
1. **Throughput (MB/sec):** How fast can lexer scan source?
   - Hand-written: 50-200 MB/sec
   - Generated (Flex): 20-100 MB/sec
   - Regex-based: 5-50 MB/sec

2. **Memory Usage:** Token objects, strings, buffers
   - Optimization: String interning for keywords

3. **Latency:** Time to first token (matters for IDE)

4. **Scaling:** Should be O(n) time, O(1) space

**Key tradeoffs:**

| Aspect | Hand-Written | Generated (Flex) |
|--------|--------------|------------------|
| Speed | Faster | Good |
| Memory | Lower | Higher (DFA tables) |
| Dev Time | Slower | Faster |
| Maintainability | Harder | Easier |
| Error Messages | Better | Generic |

**AoC lesson applied:** Simple hand-written lexer often beats complex generated one for small languages. Measure first—lexing is typically 5-10% of total compile time.

**When is performance "good enough"?**
- **Batch compiler:** 100 MB/sec is plenty
- **Interactive tools:** Latency < 100ms matters more
- **JIT compiler:** Every millisecond counts

Context determines the answer. Don't optimize until you measure and know it matters.

### Error Recovery: Finding Multiple Errors

**Goals:**
1. Continue scanning (find all errors in one pass)
2. Minimize cascading errors
3. Provide helpful context

**Recovery techniques:**

**1. Panic Mode:** Skip to synchronization point (newline, semicolon, etc.)
- Pros: Simple, fast
- Cons: May skip valid code

**2. Substitute Token:** Replace invalid with ERROR token
- Pros: Parser can continue
- Cons: May produce nonsense

**3. Minimal Distance Correction:** Guess what user meant
- Pros: Analysis continues
- Cons: Might guess wrong

**Error message quality progression:**

Bad: `Error at position 147`

Better: `Error at line 5, column 23: Unterminated string literal`

Best:
```
Error at line 5, column 23: Unterminated string literal
    x = "hello world
        ^
Expected closing quote (") before end of line
```

**Key elements:** Position, context (show source), explanation, suggestion.

**Handles:**

## Insights and Connections

### Cross-Domain Analogies That Clicked

**Chess engine perft testing ↔ Lexer invariant checking:**
Both verify that transformations preserve correctness. Perft checks legal moves produce valid positions; lexer testing checks all input consumed without gaps/overlaps.

**AoC profiling ↔ Lexer performance:**
Same lesson: measure before optimizing. Simple often wins. Don't assume complex is faster.

### Surprises Today

1. **Simple often beats complex:** Hand-written lexer can outperform generated one for small languages. The overhead of DFA tables and generic code matters.

2. **Error messages are hard:** Building helpful context requires tracking positions accurately and having good recovery strategies.

3. **Edge cases are endless:** Unicode, numeric overflow, unclosed delimiters, escape sequences—the list grows from real-world use, not theoretical design.

4. **Testing is like perft:** Same principle—verify invariants at every step. No gaps, no overlaps, all input accounted for.
