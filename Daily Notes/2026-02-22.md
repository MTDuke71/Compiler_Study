## Session Notes

### Intermediate Code (Lecture 74)

**The fundamental question:** Why not translate source directly to machine code?

**Answer:** An intermediate language provides a **sweet spot** — more detail than source (registers) but fewer details than target (not architecture-specific). This enables both optimization and retargetability.

**Three-address code:**
- Each instruction has **at most three addresses** (two sources, one destination)
- Compound expressions are decomposed: `x = y + (y * z)` becomes:
  ```
  t1 = y * z
  t2 = y + t1
  ```
- Every subexpression gets an **explicit name** — the foundation for optimization
- Unlimited registers simplify everything; register allocation is deferred

**Key insight:** Naming intermediate values is the single most important consequence. Anonymous subexpressions become named, enabling CSE, constant propagation, and dead code elimination.

**Chess engine analogy:** Like choosing a board representation that's not raw FEN (too high-level) and not a platform-specific bitboard layout (too low-level) — something in between that supports both analysis and efficient conversion.

### Optimization Framework (Lectures 75-77)

**Where optimization fits:**
```
Lexing → Parsing → Semantics → [Optimization] → Code Generation
```

In modern compilers, optimization contains **the most code** and is **the most complex** part.

**The non-negotiable invariant:** Optimization must never alter what the program computes. The answer must remain the same.

**Three granularities:**

| Granularity | Scope | Adoption |
|-------------|-------|----------|
| **Local** | Single basic block | Almost all compilers |
| **Global** | Entire CFG (one function) | Many compilers |
| **Inter-procedural** | Across function boundaries | Few compilers |

**Basic blocks** — the fundamental unit:
- Maximal sequence with no labels (except first) and no jumps (except last)
- Once you enter, you execute every instruction through to the end
- Like a **forced sequence** in chess — no branching decisions until the end

**Control flow graphs (CFGs):**
- Nodes = basic blocks, edges = possible control transfers
- Abstracts away boring parts (straight-line code) and highlights interesting parts (branches, loops, merge points)

**Local optimizations — the "bag of tricks":**

| Optimization | What It Does | Example |
|-------------|-------------|---------|
| Algebraic simplification | Eliminate identity operations | `x + 0` → delete |
| Strength reduction | Replace expensive with cheap | `x * 8` → `x << 3` |
| Constant folding | Evaluate constants at compile time | `2 + 2` → `4` |
| CSE | Reuse previously computed values | `y+z` computed twice → reuse first |
| Copy propagation | Replace copies with originals | `w = x; ... use w` → `use x` |
| Dead code elimination | Remove unused assignments | `a = b` (a never read) → delete |

**Critical pattern:** Individual optimizations are simple. Power comes from **interaction** — constant propagation enables folding, folding enables dead code elimination, and so on. The compiler repeatedly applies transformations until no more apply (fixpoint).

**Peephole optimization** (Lecture 77):
- Slides a small window (2-4 instructions) over assembly code
- Matches patterns and replaces with better sequences
- Same principle as local optimization, but at the assembly level
- Machine-specific (unlike IL optimizations)

**Important caveat:** "Program optimization" is a misnomer. Compilers don't produce *optimal* code — they produce *improved* code. More accurate term: program improvement.

### Global Dataflow Analysis (Lectures 78-82)

**The leap from local to global:**

Within a basic block, optimization is easy — there's only one path. But across basic blocks, proving a local fact (e.g., "is x constant here?") requires **global knowledge** — analyzing all possible paths through the CFG.

**The saving grace:** It's always OK to be conservative. If you can't prove a property, don't optimize. Correctness is preserved; you just miss an optimization opportunity.

**Chess analogy:** Like move ordering in alpha-beta — if you miss a good move, you search longer (slower but correct). If you prune incorrectly, you might miss the best line (broken).

#### Constant Propagation (Lecture 79) — The Flagship Forward Analysis

**Three abstract values for each variable at each program point:**

| Value | Symbol | Meaning |
|-------|--------|---------|
| **Bottom** | `⊥` | Statement never executes (unreachable) |
| **Constant** | `c` | Variable is definitely constant `c` here |
| **Top** | `⊤` | Variable is not known to be constant |

**Transfer rules (simplified):**
- **Merge from predecessors:** Take the LUB of all incoming values
- **Constant assignment** `x = c`: output is `c`
- **Non-constant assignment** `x = f(...)`: output is `⊤`
- **Doesn't assign x:** value passes through unchanged
- **Unreachable:** if input is `⊥`, output is `⊥` (highest priority)

**The algorithm:** Initialize entry to `⊤`, everything else to `⊥`. Repeatedly fix inconsistencies until fixpoint.

```
    ┌──────────┐
    │ x = 3    │
    └──┬───┬───┘
       │   │
    ┌──▼┐ ┌▼──────┐
    │...│ │ x = 4  │
    └──┬┘ └┬──────┘
       │   │
    ┌──▼───▼───┐
    │ a = 2*x  │  ← x = ⊤ here (paths disagree: 3 vs 4)
    └──────────┘
```

#### Analysis of Loops (Lecture 80) — Breaking Cycles with Bottom

**The problem:** In a loop, the value at the merge point depends on the loop body, which depends on the merge point. Circular dependency.

**The solution:** Start with `⊥` (optimistic — assume back edge is never taken), then refine iteratively.

**Why this works:**
1. `⊥` lets us treat the back edge as "doesn't exist yet"
2. Forward propagation fills in actual values
3. Back edge gets updated with what we learned
4. Re-check merge point — if consistent, fixpoint reached
5. If not, update and repeat

**Chess analogy:** Like iterative deepening — start with a shallow guess and refine. Each iteration uses the previous result as a starting point. Guaranteed to converge because each pass adds information.

#### Orderings and Lattices (Lecture 81) — The Mathematical Foundation

**The ordering on abstract values:**

```
        ⊤          ← top (most conservative, least precise)
      / | \
    ... 0  1  2 ...   ← constants (incomparable to each other)
      \ | /
        ⊥          ← bottom (most optimistic, most precise)
```

**Least Upper Bound (LUB)** — the single operation that replaces all four merge rules:

| LUB of... | Result | Why |
|-----------|--------|-----|
| `⊥, 3` | `3` | Bottom doesn't interfere |
| `3, 3` | `3` | Both agree |
| `3, 4` | `⊤` | Paths disagree → unknown |
| `⊤, anything` | `⊤` | Top absorbs everything |

**Why the algorithm terminates:**
- Values start at `⊥` and can only go **up**: `⊥ → c → ⊤`
- Each value changes at most **twice**
- Total updates bounded by **4 x (number of statements)**
- Algorithm is **linear in program size**

This is not a heuristic — it's a proof. The lattice structure with finite height guarantees convergence.

#### Liveness Analysis (Lecture 82) — The Backward Counterpart

**The question constant propagation can't answer:** After we've propagated constants, the original assignments might be dead. How do we prove it?

**Liveness:** A variable `x` is **live** at statement `s` if there exists a path forward where `x` is read before being overwritten. Otherwise, it's **dead**.

**Dead code elimination rule:** `x = ...` is dead code if `x` is dead immediately after the statement.

**Key difference from constant propagation:**

| Property | Constant Propagation | Liveness Analysis |
|----------|--------------------|--------------------|
| **Direction** | Forward | Backward |
| **Information flows** | Same as execution | Against execution |
| **Merge rule** | LUB (all paths must agree) | OR (any path suffices) |
| **Starting point** | Entry node (`⊤`) | Uses of variables |
| **Question** | "What happened in the past?" | "What will happen in the future?" |
| **Quantifier** | Universal (AND) | Existential (OR) |

**Liveness rules:**
1. **Merge from successors:** `L(x, s, out) = OR { L(x, si, in) }` — live on **any** successor path
2. **Statement reads x:** `L(x, s, in) = true` (x is live before this statement)
3. **Statement writes x (not reads):** `L(x, s, in) = false` (old value is dead)
4. **Statement ignores x:** `L(x, s, in) = L(x, s, out)` (passes through)

**Terminates in linear time** — only two abstract values (`false < true`), each changes at most once.

## The Unifying Framework

**The real lesson of Week 8:** All global dataflow analyses share the same skeleton:

1. **Local rules** propagating information between adjacent points
2. **Abstract values** with an ordering (lattice)
3. **Merge operation** (LUB)
4. **Fixpoint iteration** until consistency
5. **Monotonicity** guaranteeing termination

The specific analysis defines: what values, what transfer rules, which direction. **Everything else is the same.**

## Key Insights

### 1. Naming Is the Foundation of Optimization
Three-address code forces every subexpression to have an explicit name. This one property enables CSE, constant propagation, dead code elimination — the entire optimization toolkit. Without names, there's nothing to analyze.

### 2. Optimizations Are Simple; Interactions Are Powerful
No single optimization is complex. Constant folding? Pattern match and evaluate. Copy propagation? Textual substitution. The power comes from cascading effects — one transformation enables the next. The compiler's "bag of tricks" model works by repeated application until fixpoint.

### 3. Cost-Benefit Dominates Real Compilers
Not every known optimization gets implemented. The rule is **maximum benefit for minimum cost**. Simple optimizations (constant folding, dead code) give 90% of the speedup. The remaining 10% requires exponentially more effort.

### 4. Local Facts, Global Proofs
The optimization is local (replace `x` with `3` at one statement). The proof is global (check all paths through the CFG). Dataflow analysis bridges this gap systematically.

### 5. Conservatism Is the Safety Net
When you can't prove a property, don't optimize. The program remains correct. It's always safe to be conservative; it's never safe to be wrong.

### 6. Bottom Breaks Cycles
The need for `⊥` is **intimately tied** to loops. Without it, circular dependencies can't be broken. Start optimistic (assume back edges are unreachable), then refine until fixpoint.

### 7. The Lattice Is the Key Abstraction
The ordering `⊥ < c < ⊤` isn't just notation — it's the mathematical structure that guarantees convergence, bounds complexity, and generalizes across all analyses. Finite lattice height → guaranteed termination → linear complexity.

### 8. Forward and Backward Are Complementary
Constant propagation (forward) asks "what was defined in the past?" Liveness (backward) asks "what will be used in the future?" Together they enable the full optimization cycle: propagate constants, then eliminate the dead assignments they leave behind.
