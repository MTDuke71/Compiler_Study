## Session Notes

### Part 1: The Handle Problem (Lecture 35)

**The insight:** Just because the stack top matches `A → β` doesn't mean you should reduce. A **handle** is the "safe" reduction point — one that still allows reaching the start symbol.

**Key properties:**
- Handles always appear at stack top (never buried)
- Handles are **unique** in a rightmost derivation
- Wrong reduction = dead end (like a chess blunder)

**Chess analogy:** A handle is like a **forced sequence** — the move that keeps your winning advantage. A non-handle is a plausible-looking move that actually loses.

---

### Part 2: LR(0) Items (Lecture 36)

**The formalism:** An item `A → α • β` says "I've seen α, expecting β."

```
E → • int         (haven't started)
E → int •         (complete, ready to reduce)
E → E • + T       (seen E, expecting + T)
```

**Key insight:** The stack isn't random symbols — it's a **stack of partial right-hand sides**. Each item tracks progress in one production, and items nest (like function calls on a call stack).

**The "0" in LR(0):** Zero lookahead *for items* — we don't track what comes after. Not epsilon, not "zero input" — zero lookahead built into the item notation.

---

### Part 3: The Viable Prefix NFA (Lecture 37)

**The construction:**
1. States = LR(0) items
2. Symbol transitions: `[A → α • X β] --X--> [A → α X • β]`
3. Epsilon transitions: `[A → α • B β] --ε--> [B → • γ]` for all `B → γ`

**What it does:** Reads the stack bottom-to-top. If NFA accepts, stack is a **viable prefix** (could lead to valid parse). If stuck, parse error.

**The magic:** Viable prefixes form a **regular language** — despite CFG being more powerful, the *set of valid parse states* is regular!

---

### Part 4: The LR(0) DFA (Lecture 38)

**Subset construction:** Convert NFA to DFA. Each DFA state is a **set of items** — all the NFA states we could be in.

**Valid items:** Item `[A → α • β]` is valid for stack `γ` if DFA reaches a state containing that item after reading `γ`.

**Key operations:**
- **GOTO(I, X):** Advance dot past X in all items, then ε-close
- **CLOSURE(I):** Add all items reachable via ε-transitions

**Chess analogy:** DFA state is an evaluated position — summarizes all possible continuations without tracking each line separately.

---

### Part 5: SLR(1) Parsing (Lecture 39)

**The algorithm:**
1. Build LR(0) DFA
2. If state has `[A → α •]`, reduce on input `a` only if `a ∈ FOLLOW(A)`
3. If state has `[A → α • a β]`, shift on input `a`

**Why FOLLOW?** If we reduce `A → α`, the next symbol must be something that can legally follow A in *some* derivation.

**Conflict detection:**
- **Shift-reduce:** State has both `[A → α •]` and `[B → β • a γ]` where `a ∈ FOLLOW(A)`
- **Reduce-reduce:** State has `[A → α •]` and `[B → β •]` where `FOLLOW(A) ∩ FOLLOW(B) ≠ ∅`

---

### Part 6: Parsing Example (Lecture 40)

**Trace of `int * int` with grammar E → E * T | T, T → int:**

| Step | Stack | Input | Action |
|------|-------|-------|--------|
| 0 | ε | int * int $ | Shift |
| 1 | int | * int $ | Reduce T → int |
| 2 | T | * int $ | Reduce E → T |
| 3 | E | * int $ | Shift |
| 4 | E * | int $ | Shift |
| 5 | E * int | $ | Reduce T → int |
| 6 | E * T | $ | Reduce E → E * T |
| 7 | E | $ | Accept |

**Critical insight:** After each reduce, we **re-run DFA from bottom of stack** to find new state. The next lecture fixes this inefficiency.

---

### Part 7: State Stack Optimization (Lecture 41)

**The problem:** Re-running DFA after every reduce is O(n) per step → O(n²) total.

**The solution:** Store **(symbol, state)** pairs on stack. The state records "DFA state after reading everything below."

After reduce, don't re-scan — just look up `GOTO(stack_state, LHS)`.

**This is memoization!** 🎯

**Chess engine analogy:**
- **Without state stack:** Like recalculating piece positions from initial position after every move
- **With state stack:** Like incrementally updating position — only change what moved

**The tables:**
- **ACTION[state, terminal]:** shift/reduce/accept/error
- **GOTO[state, nonterminal]:** next state after reduction

**Chess analogy for tables:**
- **GOTO:** Precomputed bitboard move tables — given position + piece, instantly look up moves
- **ACTION:** Endgame tablebase — given position, look up perfect play

---

### Part 8: Conflict Examples (Lecture 42)

**Example 1: S → S A | B** — IS SLR(1)
- 4 states, clean separation
- FOLLOW(S') = {$}, FOLLOW(S) = {$, A}
- No overlap with shift symbols ✓

**Example 2: S → S A S | B** — NOT SLR(1)
- 5 states, conflict in state with `[S → S A • S]` and `[S → S A S •]`
- Can shift A (expecting more S A S pattern)
- Can reduce S → S A S on A (since A ∈ FOLLOW(S))
- Parser can't decide!

**Why FOLLOW fails:** FOLLOW is *global* — "what can follow S anywhere?" But context matters: *this particular S* might have restricted followers. LR(1) items fix this by tracking lookahead per-item.

## Key Insights

### 1. Regular Languages Hidden in Context-Free Parsing
The set of viable prefixes (valid stacks) is **regular**, even though the grammar is context-free. This is why we can use a DFA for parsing!

### 2. State Stack = Memoization
The optimization in lecture 41 is pure dynamic programming. We cache intermediate results (DFA states) to avoid recomputation. Same pattern as chess engine incremental updates.

### 3. Tables are Precomputation
ACTION and GOTO tables are like chess bitboards or endgame tablebases — expensive to build, O(1) to query. All the "thinking" happens at table-generation time, not parse time.

### 4. FOLLOW Sets are Global (Too Coarse)
SLR uses FOLLOW(A) to decide reductions, but FOLLOW is global. LR(1) items track lookahead *per item*, enabling finer distinctions. LALR(1) compromises: LR(1) power, SLR(1) table size.

### 5. Conflicts = Ambiguity in Automation
A shift-reduce conflict means the grammar has a point where the *automaton* can't decide. This doesn't mean the grammar is ambiguous (semantic!) — it means the *heuristic* (SLR) isn't powerful enough.
