## Session Notes

### Why IR Exists

**Problem with AST:**
ASTs are designed to preserve source code structure, not to enable transformation. They're great for pattern matching and maintaining the hierarchical nature of code, but they make optimization difficult:

- **Tree structure is awkward for sequential analysis** - Walking nested trees repeatedly is inefficient
- **Control flow is implicit** - Where do if/while/goto actually jump? Not obvious in AST
- **Expression nesting complicates analysis** - Finding common subexpressions in deeply nested trees is hard
- **No explicit temporaries** - Data flow isn't visible

**Example:**
```c
x = a + b * c;

// AST form (preserves structure but hides data flow)
Assignment
  ├── x
  └── Add
      ├── a
      └── Multiply
          ├── b
          └── c

// IR form (makes data flow explicit)
t1 = b * c
t2 = a + t1
x = t2
```

**Why IR is better:**
- **Linear representation** - Easy to iterate over, process sequentially
- **Atomic operations** - Each instruction does one thing: `result = operand1 op operand2`
- **Explicit control flow** - CFG shows all possible execution paths
- **Explicit data flow** - SSA form shows exactly where values come from and go to
- **Platform-independent** - Not yet tied to x86 or ARM specifics

The IR is the "working form" - it's designed for the compiler's needs, not the programmer's.

### What Optimization Does

**Core idea:** Transform IR to better IR while preserving semantics (the master invariant).

**What "better" means:**
- Faster execution (most common goal)
- Smaller binary size (embedded systems, web delivery)
- Lower power consumption (mobile devices)
- Reduced memory usage

**How IR enables it:**

1. **Constant Folding** (easiest)
   ```
   // Before
   x = 2 + 3
   
   // After
   x = 5
   ```
   Requires: Recognizing constant expressions (easy in IR, hard in nested AST)

2. **Dead Code Elimination**
   ```
   // Before
   x = 5
   y = x + 1
   // y is never used after this
   
   // After
   x = 5
   // y eliminated
   ```
   Requires: Data flow analysis to track which values are used (CFG + SSA make this visible)

3. **Common Subexpression Elimination**
   ```
   // Before
   a = b + c
   d = b + c  // Same computation!
   
   // After
   a = b + c
   d = a      // Reuse result
   ```
   Requires: Seeing that two expressions compute the same value (IR makes this obvious)

4. **Loop Invariant Code Motion**
   ```
   // Before
   for (i = 0; i < n; i++) {
       x = y + z;  // y and z don't change in loop!
       a[i] = x;
   }
   
   // After
   x = y + z;  // Move outside loop
   for (i = 0; i < n; i++) {
       a[i] = x;
   }
   ```
   Requires: Control flow graph to identify loops, data flow to detect invariants

**The tradeoff:** More optimization = slower compilation, but faster execution. Different build modes make different choices (debug: `-O0`, release: `-O2` or `-O3`).

**Critical constraint:** Observable behavior must not change. Faster wrong code is still wrong!

### What Code Generation Produces

**Input:** Platform-independent IR (still abstract - unlimited temporaries, generic operations)

**Output:** Platform-specific machine code or bytecode (concrete - real registers, actual instructions)

**Three main tasks:**

**1. Instruction Selection**
Map IR operations to target machine instructions. This is non-trivial because:
- One IR operation might map to multiple machine instructions
- Multiple instruction sequences might do the same thing (choose fastest/smallest)
- Different architectures have different instruction sets

Example:
```
// IR
t1 = a + b

// x86 (two-address, destroys source)
mov rax, a
add rax, b    ; rax = rax + b (t1 now in rax)

// ARM (three-address, preserves sources)
add r0, r1, r2  ; r0 = r1 + r2 (cleaner!)
```

**2. Register Allocation**
The IR has unlimited temporaries (`t1, t2, t3, ...`) but the CPU has limited registers (x86: ~6-14 usable, ARM: ~14-30).

Must assign temporaries to physical registers. When you run out: **spilling** (save to stack).

Example:
```
// IR (4 live temporaries)
t1 = a + b
t2 = c + d
t3 = t1 * t2
t4 = t3 + e

// If we only have 2 registers available:
mov rax, a
add rax, b       ; t1 in rax
mov [rsp-8], rax ; SPILL t1 to stack (slow!)
mov rax, c
add rax, d       ; t2 in rax
mov rbx, [rsp-8] ; RELOAD t1 from stack
imul rbx, rax    ; t3 in rbx
add rbx, e       ; t4 in rbx
```

Spilling is expensive (memory access >> register access). Good register allocation is critical for performance.

**Two main algorithms:**
- **Linear scan:** Simple, fast compilation, ~95% as good as optimal (used in JITs)
- **Graph coloring:** Complex, slow compilation, near-optimal quality (used in optimizing compilers)

**3. Instruction Scheduling**
Modern CPUs execute multiple instructions in parallel (superscalar, out-of-order execution). Arrange instructions to maximize parallelism.

Example:
```
// Bad: data dependencies cause stalls
mov rax, [x]
add rax, 1     ; must wait for load to complete
mov rbx, [y]
add rbx, 2     ; must wait for load to complete

// Better: overlap independent operations
mov rax, [x]
mov rbx, [y]   ; start second load while first completes
add rax, 1     ; by now rax is ready
add rbx, 2     ; by now rbx is ready
```

**Result:** Executable machine code or bytecode that runs on actual hardware.

### The Complete Pipeline

```
SOURCE CODE (text)
    ↓
[1. LEXING]
    Characters → Tokens
    Invariant: Well-formed tokens (type, value, position)
    ↓
[2. PARSING]
    Tokens → AST
    Invariant: Syntactically valid tree structure
    ↓
[3. SEMANTIC ANALYSIS]
    AST → Annotated AST + Symbol Table
    Invariant: Types correct, variables declared, scopes valid
    ↓
[4. IR GENERATION]
    AST → IR (TAC, CFG, SSA)
    Invariant: Semantics preserved, control/data flow explicit
    ↓
[5. OPTIMIZATION]
    IR → Better IR
    Invariant: Same observable behavior, improved metrics
    ↓
[6. CODE GENERATION]
    IR → Machine Code/Bytecode
    Invariant: Semantics preserved, executable on target
    ↓
EXECUTABLE
```

**Why this order?**

Each phase builds on invariants from the previous:
- **Parser** assumes tokens are well-formed (lexer's job)
- **Semantic analyzer** assumes AST is syntactically valid (parser's job)
- **IR generator** assumes types and scopes are correct (semantic analyzer's job)
- **Optimizer** assumes IR is well-formed (IR generator's job)
- **Codegen** assumes IR is optimized and valid (optimizer's job)

**Why optimize before codegen?**

Optimizing at IR level is:
- **Platform-independent** - Write optimization once, works for all targets
- **Higher-level** - Easier to see semantic equivalences
- **More powerful** - Can make assumptions that machine code can't

Optimizing machine code directly:
- **Platform-specific** - Must rewrite for each target
- **Lower-level** - Harder to see what code means
- **Limited** - Can only do micro-optimizations

**Best practice:** Major optimization at IR level, final tuning at machine code level.

**Key Realizations:**
1. **Control flow is state transitions** - Programs are state machines, control flow determines which transitions happen. Understanding this makes CFGs intuitive.

2. **Invariants are contracts between phases** - Like perft testing in chess engines, invariants give you a "checksum" for correctness. Each phase can assume previous invariants hold without re-checking.

3. **All design choices are tradeoffs** - Simple can beat complex (linear scan in production!), more optimization isn't always better (diminishing returns), context determines the right choice. Measure, don't guess (AoC lesson applies here too).

4. **Multiple representations aren't redundant** - Each IR (AST, TAC, CFG, SSA) is optimized for different operations. The compiler pipeline is a series of transformations between representations, each enabling the next phase.

## Week 2 Reflection

**What was the biggest insight this week?**

The realization that multiple representations aren't "doing the same thing multiple ways" - they're each optimized for fundamentally different operations. AST preserves structure (good for pattern matching, bad for control flow). IR makes flow explicit (good for optimization, bad for initial generation). This is why the pipeline exists: each transformation converts to a representation better suited for the next task.

Also: the chess engine parallels keep reinforcing understanding. Invariants = perft (checksums for correctness). Tradeoffs = depth vs. evaluation. Representations = board representation choices. Having concrete analogies from another domain makes abstract concepts stick.

**How does the complete pipeline fit together?**

Six phases, each transforming representation while maintaining invariants:
1. Lex: text → tokens (grammar's alphabet)
2. Parse: tokens → AST (syntactic structure)
3. Analyze: AST → annotated AST + symbols (semantic meaning)
4. IR Gen: AST → IR (optimization-friendly form)
5. Optimize: IR → better IR (preserve semantics, improve metrics)
6. Codegen: IR → machine code (concrete execution)

Each phase *trusts* previous invariants (doesn't re-check everything) and *provides* new guarantees for the next. It's a pipeline of increasing specificity: from abstract source text to concrete executable.
