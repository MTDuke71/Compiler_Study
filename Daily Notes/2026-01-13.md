### Key Questions to Answer

1. **How is compilation a series of state transformations?**
   - Each compiler phase takes one representation (state) and transforms it into another
   - The transformation is deterministic and meaning-preserving
   - State transitions: Characters → Tokens → AST → Annotated AST → IR → Optimized IR → Machine Code
   - Each transition makes implicit information explicit
   - The pipeline is a state machine where each phase is a transition function

2. **What does "state" mean at each phase (tokens, AST, IR, etc.)?**
   - **Characters**: Raw bytes/text with no structure
   - **Tokens**: Sequence of classified symbols with boundaries defined
   - **AST**: Tree structure representing syntactic relationships
   - **Annotated AST**: AST with types, scopes, and semantic information attached
   - **IR**: Explicit control flow and data flow (CFG, three-address code, SSA)
   - **Optimized IR**: IR with redundancies removed, constants folded
   - **Machine Code**: Binary instructions ready for execution
   - Each state is progressively more explicit and less ambiguous

3. **How do control flow and data flow relate to program state?**
   - **Control flow**: The possible execution paths through the program (which statements execute in what order)
   - **Data flow**: How values move through the program (from definitions to uses)
   - **State** is the combination of control location + data values at any point
   - Control flow determines what state transitions are possible
   - Data flow tracks how state values propagate and change
   - IR makes both explicit: CFG shows control flow, SSA shows data flow
   - Optimization analyzes state to prove transformations are safe

4. **What state invariants must hold throughout compilation?**
   - **Meaning preservation**: Program behavior must not change
   - **Well-formedness**: Each representation must be valid for its phase
   - **Type safety**: Types must remain consistent (after semantic analysis)
   - **Scope rules**: Name resolution must be consistent
   - **Control flow validity**: All paths must be reachable or explicitly unreachable
   - **Data flow consistency**: Values must be defined before use
   - **Breaking these invariants = compiler bug**

## Session Notes

### Compilation as State Transformation

Viewing compilation through the lens of state machines reveals the fundamental nature of the process:

**The Core Metaphor:**
- Source code is the *initial state*
- Machine code is the *final state*
- Each compiler phase is a *state transition function*
- The compiler is a deterministic state machine

**State Evolution:**
```
State₀: "x = 3 + 4 * 5"                    [Characters]
  ↓ Lexing
State₁: [IDENT(x), EQUALS, INT(3), ...]   [Tokens]
  ↓ Parsing
State₂: Assign(x, Add(3, Mul(4, 5)))      [AST]
  ↓ Semantic Analysis
State₃: Assign(x:int, Add(3:int, ...))    [Typed AST]
  ↓ IR Translation
State₄: t1=4*5; t2=3+t1; x=t2             [IR]
  ↓ Optimization
State₅: x=23                               [Optimized IR]
  ↓ Code Generation
State₆: mov [rbp-4], 23                    [Machine Code]
```

Each state has more **explicit** information than the previous:
- Tokens make boundaries explicit
- AST makes structure explicit
- Typed AST makes types explicit
- IR makes control flow explicit
- Optimized IR makes constant values explicit
- Machine code makes execution explicit

### State at Each Phase

**Character State** (Pre-lexing)
- Type: Unstructured byte sequence
- Ambiguity: Symbol boundaries unknown
- Invariants: Valid encoding (UTF-8, ASCII)

**Token State** (Post-lexing)
- Type: Sequence of classified symbols
- Ambiguity: Structure/precedence unknown
- Invariants: Each token has type, value, position

**AST State** (Post-parsing)
- Type: Tree of syntactic constructs
- Ambiguity: Meaning unknown (what is `x`?)
- Invariants: Valid syntax, proper nesting

**Typed AST State** (Post-semantics)
- Type: Tree with types and resolved names
- Ambiguity: Execution order/data flow implicit
- Invariants: Type-safe, names resolved, scopes valid

**IR State** (Post-IR translation)
- Type: Control flow graph with data flow
- Ambiguity: Contains inefficiencies
- Invariants: All control flow explicit, SSA form (if used)

**Optimized IR State** (Post-optimization)
- Type: Improved CFG with redundancy removed
- Ambiguity: Not mapped to machine
- Invariants: Semantically equivalent to unoptimized IR

**Machine Code State** (Post-codegen)
- Type: Binary instructions for target CPU
- Ambiguity: None—fully explicit
- Invariants: Valid instruction encoding, proper calling convention

### Control Flow + Data Flow = Program State

**Control Flow** answers: "Where am I in the program?"
- Which statement executes next?
- What are the possible execution paths?
- Represented as: CFG (Control Flow Graph)

**Data Flow** answers: "What values exist and where did they come from?"
- Where is variable `x` defined?
- Where is `x` used?
- What value does `x` hold?
- Represented as: Def-use chains, SSA (Static Single Assignment)

**Combined: Program State**
```
Program State = (Control Location, Variable Values)

Example:
  Location: Line 5 (after assignment)
  Values: {x: 23, y: 10, z: undefined}
```

**Why This Matters:**
- Optimizations must prove they preserve all reachable states
- A transformation is safe if it produces the same state at observable points
- Compiler correctness = preserving the state space of valid executions

### State Invariants Throughout Compilation

**Phase-Specific Invariants:**

1. **Lexing Output:**
   - Every token has a source location
   - No overlapping tokens
   - Token stream covers entire source

2. **Parsing Output:**
   - AST is well-formed (valid tree structure)
   - All syntax rules satisfied
   - Every node has a source location

3. **Semantic Analysis Output:**
   - All names are resolved
   - All types are checked and valid
   - Scope rules are enforced
   - No illegal operations

4. **IR Output:**
   - All control flow is explicit
   - All data flow is traceable
   - Every variable is defined before use
   - CFG has single entry and exit

5. **Optimization Output:**
   - Observable behavior unchanged
   - Semantic equivalence preserved
   - IR remains well-formed

6. **Code Generation Output:**
   - Valid machine instructions
   - Calling convention followed
   - Register allocation is valid
   - Stack frame properly maintained

**Cross-Phase Invariants:**
- **Meaning preservation**: The program's observable behavior never changes
- **Traceability**: Can map from machine code back to source line
- **Determinism**: Same input always produces same output (given same options)

## Insights

- **Compilation is just state transformation**: Each phase is simply converting one representation of the program into another, more explicit form. There's nothing magical about it.

- **Ambiguity removal = making state explicit**: Every phase takes implicit information and makes it explicit in the new state representation. Parsing makes precedence explicit, semantics makes types explicit, IR makes control flow explicit.

- **State invariants are compiler correctness**: If a phase violates its output invariants, every subsequent phase will fail or produce incorrect code. Invariants are not optional—they're the contract.

- **Control + Data = Complete State**: You cannot understand program state without both control flow (where you are) and data flow (what values you have). IR makes both explicit simultaneously.

- **Optimization is state equivalence**: An optimization is valid if and only if it preserves the state space—the set of all possible (control location, variable values) pairs the program can reach.

- **Each state has a representation cost**: More explicit states (IR, machine code) are easier to analyze but more verbose. Less explicit states (source code) are compact but ambiguous. The compiler trades between these.
