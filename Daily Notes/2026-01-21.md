## Session Notes

### Core Lexer Structure

**The Three-Part Engine:**
1. **State Management:** Current position, lookahead buffer, line/column tracking
2. **Token Recognition:** Pattern matching with maximal munch
3. **Error Recovery:** How to proceed when input doesn't match any pattern

**Like chess board representation:** The internal state (position, lookahead) is optimized for the operations you need to perform (peek, advance, backtrack).

### Maximal Munch Principle

**Rule:** Always consume the longest possible token that matches.

**Example:** `>=` should be one token (GREATER_EQUAL), not `>` followed by `=`.

**Implementation:**
- Look ahead to see if longer match is possible
- Commit only when you know no longer match exists
- Backtrack if necessary (rare in well-designed lexers)

**Chess analogy:** Like move generation - you explore possibilities before committing to a move.

### Position Tracking

**Must track:**
- Absolute position in input
- Line number (for error messages)
- Column number (for error messages)
- Start position of current token

**Why it matters:** Error messages like "line 42, column 15: unterminated string" require accurate tracking throughout scanning.

**Update on:** Every character consumed, with special handling for newlines.

### Lookahead Patterns

**Single character lookahead:**
```
if (current == '=' && peek() == '=')
    return EQUAL_EQUAL;
else if (current == '=')
    return EQUAL;
```

**Unbounded lookahead (strings, comments):**
- Scan until closing delimiter or EOF
- Must track positions across multiple lines
- Error handling for unterminated cases

**AoC lesson:** Simple lookahead (peek one character) handles 90% of cases. Complex lookahead only when necessary.

### Extension Points

**Adding string literals:**
- Recognize opening quote
- Scan until closing quote (handling escapes)
- Build string value (processing escape sequences)
- Handle errors (unterminated, invalid escapes)

**Adding floats:**
- Extend number scanning to recognize decimal point
- Handle exponential notation (1.5e10)
- Edge case: `.5` vs `5.` vs `5.0`

**Adding comments:**
- Line comments: scan until newline
- Block comments: scan until closing delimiter
- Challenge: nested block comments (requires counting depth)

### Error Handling Strategy

**Invalid character:** Skip and report, continue scanning

**Unterminated string:** Report position where string started, return ERROR token

**Numeric overflow:** Report warning, return token with clamped value

**The invariant:** Lexer always produces a token stream, even for invalid input. Parser handles semantic errors.

## Insights

### Lexer is a State Machine Walker

Hand-written lexer = explicit DFA walker. Each `if/else` branch is a state transition. The "state" is implicit in the code structure.

**This explains:** Why DFA theory matters even for hand-written lexers - you're implementing the same model manually.

### Maximal Munch is Greedy but Local

Maximal munch commits as soon as it knows the longest match. It doesn't look ahead to see if a shorter token would lead to better overall parse.

**Example:** `ifx` lexes as identifier `ifx`, not keyword `if` + identifier `x`, even if the latter would parse correctly.

**This is why:** Lexer and parser are separate. Lexer is greedy and local; parser handles global structure.

### Position Tracking is Surprisingly Tricky

Newlines, tabs, Unicode, all complicate position tracking. Off-by-one errors are common.

**Test extensively:** Position tracking is easy to get subtly wrong.

### Error Recovery at Lexer Level is Simple

Unlike parser error recovery (complex), lexer just skips invalid characters and continues. The parser will catch semantic errors.
