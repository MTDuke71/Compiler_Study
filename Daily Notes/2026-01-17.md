## Key Concepts Learned

### Compiler Fundamentals
- **Compiler phases:** Lexing → Parsing → Semantics → IR → Optimization → Codegen
- **Each phase removes ambiguity** progressively
- **Pipeline is necessary**, not optional
- **Separation of concerns** makes implementation tractable

### Economy of Languages
- **Application domains have conflicting needs** → multiple languages inevitable
- **Programmer training is dominant cost** → popular languages change slowly
- **New languages fill voids** when new domains emerge
- **No universally accepted metric** for "good" language
- **COOL optimized for compiler implementation**, not programmer productivity

### COOL Language Features
- **Single inheritance** - Can only inherit from one class
- **Expression-based** - Everything is an expression, no statements
- **Static typing** - All types explicitly declared
- **Automatic memory management** - Garbage collection
- **Keywords close constructs:** `fi`, `pool`, `esac` (easier to parse)
- **Assignment:** `<-` (not `=` which is comparison)
- **Comments:** `--` single-line, `(* ... *)` multi-line

### COOL Syntax Patterns
- **Multiple `let` bindings:** Comma-separated, later bindings can use earlier ones
- **`isvoid` test:** Check for null/void (no `null` keyword)
- **Getting void:** Declare variable without initialization
- **`case` construct:** Runtime type dispatch (pattern matching)
- **Method chaining:** Return `self` from init methods

## Insights

### Design Philosophy
**COOL's quirks all serve one goal:** Make compiler implementation achievable in one semester.
- Explicit syntax (`fi`, `pool`) → easier parsing
- No type inference → simpler semantic analysis  
- Minimal features → less code to write
- **Pareto principle:** 80% functionality, 20% effort

### Cross-Domain Connections

**Chess Engine Analogy:**
- Recursive vs iterative factorial = recursive vs iterative perft
- Simple eval + deep search = COOL's minimal features + complete implementation
- Getting 80% working quickly vs final 20% polish

**AoC Analogy:**
- Incremental development (echo → convert → stub → implement)
- Measure before optimizing (lexer performance usually negligible)
- Different tools for different problems (no "best" language)

### Implementation Preview
Every COOL feature demonstrated has compiler implications:
- **`let` bindings** → variable scoping, symbol tables
- **Control flow** (`if`, `while`) → branches and labels in assembly
- **Type conversion** (`a2i`) → non-trivial runtime code
- **Linked lists** → AST node structures
- **`case` construct** → how compiler processes heterogeneous ASTs

## Questions Raised

1. **Self-hosting:** How does Rust compiler (written in Rust) get compiled?
   - Bootstrap with previous version
   - Originally written in OCaml, then self-hosted
   
2. **OCaml vs Rust for compiler implementation:**
   - OCaml: traditional academic choice, excellent for prototyping
   - Rust: modern alternative with similar benefits + better performance
   - Recommendation: Use C++/Java for Stanford course, Rust for post-course projects

3. **Command-line arguments in COOL:**
   - `main()` takes no arguments (simplifies compiler)
   - Workarounds: stdin, files, hard-coding
   - Could extend language as optional enhancement

4. **Memoization in COOL:**
   - Possible but requires building data structures from scratch
   - No built-in HashMap/arrays
   - Perfect illustration of production vs teaching language tradeoffs

5. **Why `fi`/`pool` keywords?**
   - Unambiguous closing (parser knows what's being closed)
   - Better error messages
   - Simpler grammar (no context tracking for generic `}`)
   - Design optimized for compiler ease, not programmer convenience
