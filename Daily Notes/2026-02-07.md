## Session Notes

### Part 1: Why Semantic Analysis? (Lecture 43)

**The insight:** Lexing finds bad characters, parsing finds bad structure, but **most programmer errors are semantic**:
- Undeclared variables
- Type mismatches (`x + "hello"`)
- Inheritance cycles
- Wrong argument counts

**The expressiveness hierarchy:**

```
Regular Expressions  →  Can't count (no nested parens)
Context-Free Grammars  →  Can't enforce context (no "declared before use")
Semantic Analysis  →  Turing-complete checks (but must terminate)
```

**Chess analogy updated:**
- Lexing: Is this valid algebraic notation? (`e4` not `z9`)
- Parsing: Is the move format complete? (`Nxe4+` not `Nx+`)
- **Semantics: Is this move legal in the current position?** ← Needs board state!

Just like chess validation needs the current position, semantic analysis needs the **symbol table** (what's been declared).

### Part 2: Scope — Matching Names to Meanings (Lecture 44)

**The core problem:** When you write `x + 1`, which `x`?

```cool
let x : Int <- 0 in
    let x : Int <- 1 in
        x + x      -- Inner x (value 1)
    + x            -- Outer x (value 0)
```

**Most-closely-nested rule:** At any program point, an identifier refers to the **closest enclosing declaration**.

**Two scoping strategies:**

| Strategy | Binding Time | Example Language |
|----------|--------------|------------------|
| **Static (lexical)** | Compile time from text | Cool, C, Java, Python |
| **Dynamic** | Runtime from call stack | Old Lisp, bash variables |

**Why static wins:**
- Predictable (can see bindings by reading code)
- Optimizable (compiler knows what's what)
- Catches errors early (undeclared = compile error)

**Cool's scoping rules:**
- Class attributes visible throughout class
- Method parameters visible in method body
- `let` bindings visible in their body
- Shadowing allowed (inner `let x` hides outer `x`)

**Key insight:** Scope is the first truly **context-sensitive** analysis — the meaning of `x` depends on *where* it appears, not just *what* it says.

### Part 3: Symbol Tables — Tracking What's In Scope (Lecture 45)

**Definition:** A symbol table answers "What identifiers are currently in scope, and what do we know about them?"

**Core operations:**
- `add(name, info)` — enter scope, bind name
- `lookup(name)` → info — find what name means
- `remove(name)` — exit scope, unbind name

**Implementation for nested scopes: Stack of hash tables**

```
┌──────────────────┐  ← Current scope (innermost let)
│ x ↦ Int (value 1)│
├──────────────────┤
│ x ↦ Int (value 0)│  ← Outer let
├──────────────────┤
│ y ↦ String       │  ← Class attributes
└──────────────────┘
```

Lookup scans from top to bottom — first match wins (most-closely-nested).

**Chess engine analogy:**
- **Symbol table structure:** Like incremental position updates (Zobrist hashing)
- **Lookup:** Like querying piece square tables
- **Entering scope:** Like making a move (push new state)
- **Exiting scope:** Like unmaking a move (pop state)

**The traversal pattern:**

```python
def check_let(expr: Let):
    # PRE-ORDER: Enter scope
    symbol_table.add(expr.name, expr.type)
    
    # RECURSE: Check children
    check(expr.init)
    check(expr.body)
    
    # POST-ORDER: Exit scope
    symbol_table.remove(expr.name)
```

**Critical lesson:** Don't fight multiple passes. Cool requires **three passes**:
1. Gather all class names (so inheritance can reference any class)
2. Check inheritance graph (detect cycles)
3. Type check methods and expressions

Simple passes beat complex single-pass attempts.

### Part 4: Types — Enforcing Intended Interpretation (Lecture 46)

**Definition:** A type is:
1. A set of values (the domain)
2. A set of operations defined on those values

| Type | Values | Operations |
|------|--------|------------|
| `Int` | ..., -1, 0, 1, 2, ... | `+`, `-`, `*`, `/`, `<`, `==` |
| `String` | "", "a", "hello", ... | `concat`, `length`, `substring` |
| `Bool` | true, false | `and`, `or`, `not`, `if` |

**Why types matter:** At the assembly level, everything is bits. The CPU will happily execute:
```asm
add R1, R2, R3    ; Add function pointer + float = garbage
```

**Types prevent meaningless operations from reaching the machine.**

**Three purposes of types:**

| Purpose | Benefit | Example |
|---------|---------|---------|
| **Catch errors** | Before they corrupt data | Can't add strings to ints |
| **Document code** | Types are contracts | `distance(Point, Point) → Int` |
| **Enable optimization** | Compiler knows sizes, layouts | Int = 32 bits, predictable |

**Static vs. Dynamic debate:**
- **Static (Cool, Java, Rust):** Check at compile time, reject bad programs early, zero runtime cost
- **Dynamic (Python, JavaScript):** Check at runtime, maximum flexibility, runtime overhead

**Cool's position:** Purely static, structurally typed (inheritance hierarchy), no coercion.

**AoC analogy:** Types are like puzzle constraints:
- Static typing: Reject wrong solutions before running (parse format, check constraints)
- Dynamic typing: Run and fail fast if wrong (try it, ValueError if bad)

Both work, different tradeoffs.

### Part 5: Type Checking — Inference Rules and Proof Trees (Lecture 47)

**The formalism:** Type checking is **provability**. We build logical proofs that expressions have certain types.

**Inference rule notation:**

```
Premise₁    Premise₂    ...    Premiseₙ
─────────────────────────────────────
           Conclusion
```

Read as: "If all premises hold, then conclusion follows."

**Example: Addition rule**

```
⊢ e₁ : Int    ⊢ e₂ : Int
──────────────────────────
    ⊢ e₁ + e₂ : Int
```

"If e₁ has type Int AND e₂ has type Int, THEN e₁ + e₂ has type Int."

**Proof trees have the same structure as AST:**

```
        e₁ + e₂ : Int
       /            \
  e₁ : Int      e₂ : Int
     |             |
   3 : Int      4 : Int    (axioms — no premises)
```

**Type checking = tree traversal:**
- Leaves (literals): Axioms, types given
- Interior nodes: Combine children's types per rules
- Root: Final type of entire expression

**Soundness:** If we can build a proof tree, the program is type-safe. "Well-typed programs don't go wrong."

**The three formalisms completed:**

| Phase | Formalism | Proves |
|-------|-----------|--------|
| Lexing | Regular Expressions | This is a valid token stream |
| Parsing | CFGs | This is valid structure (AST) |
| Type Checking | **Inference Rules** | **This is valid semantically** |

### Part 6: Type Environments — Giving Context to Free Variables (Lecture 48)

**The problem:** What's the type of `x`?

```cool
x + 1
```

**Can't tell from `x` alone!** Need context: what was `x` declared as?

**Type environment O:** A function mapping variable names to types.

```
O = { x ↦ Int, y ↦ String, z ↦ Bool }
```

**New notation for rules:**

```
O ⊢ e : T
```

Read as: "Under environment O, expression e has type T."

**Updated addition rule:**

```
O ⊢ e₁ : Int    O ⊢ e₂ : Int
────────────────────────────
    O ⊢ e₁ + e₂ : Int
```

Same premises, but now **environment flows through**.

**How `let` extends the environment:**

```
O ⊢ e₀ : T₀    O[x ↦ T] ⊢ e₁ : T₁
─────────────────────────────────
O ⊢ let x : T <- e₀ in e₁ : T₁
```

- Check init expression `e₀` under current environment O
- Check body `e₁` under **extended** environment O[x ↦ T]
- The body's type becomes the whole `let`'s type

**The two-phase pattern emerges:**
- **Environments flow DOWN** (parent to children, accumulating bindings)
- **Types flow UP** (children to parent, computing results)

**Chess analogy:**
- **Environment O:** Current board position (what pieces are where)
- **Extending O:** Making a move (new position)
- **Checking e under O:** Is this move legal in this position?

### Part 7: Subtyping — When Types Form a Hierarchy (Lecture 49)

**The problem:** Exact type matching is too restrictive.

```cool
let x : Animal <- new Dog in    -- Dog ≠ Animal, reject?
    x.speak()
```

But `Dog` inherits from `Animal`! A `Dog` **is an** `Animal` — should work.

**Subtyping relation: X ≤ Y**

Read as: "X is a subtype of Y" or "X can be used wherever Y is expected."

**Cool's subtyping rules:**
1. **Reflexivity:** `X ≤ X` (everything is a subtype of itself)
2. **Transitivity:** If `X ≤ Y` and `Y ≤ Z`, then `X ≤ Z`
3. **Inheritance:** If `X` inherits from `Y`, then `X ≤ Y`
4. **Top type:** `X ≤ Object` for all types (Object is the root)

**Updated let rule with subtyping:**

```
O ⊢ e₀ : T₀    T₀ ≤ T    O[x ↦ T] ⊢ e₁ : T₁
──────────────────────────────────────────
    O ⊢ let x : T <- e₀ in e₁ : T₁
```

Key change: `T₀ ≤ T` (init type must be **subtype** of declared type).

**Least upper bound (lub):**

When combining types (like in `if-then-else`), we need the **smallest common ancestor** in the inheritance tree:

```
if pred then new Dog else new Cat
```

Must return type that covers both `Dog` and `Cat` → `Animal` (if both inherit from Animal).

**Computing lub:** Walk up inheritance tree from both types until paths meet.

**Chess analogy:**
- **Subtyping:** Like piece values (Knight ≤ Piece, Queen ≤ Piece)
- **Lub:** Like finding common threats (both pieces attack which squares?)

### Part 8: Typing Methods — The Three Environments (Lecture 50)

**New complexity:** Methods and objects live in **different namespaces**.

```cool
class Example {
    foo : Int;           -- Object 'foo'
    foo() : String {...} -- Method 'foo' (no conflict!)
}
```

**The three environments emerge:**

| Component | Maps | Purpose |
|-----------|------|---------|
| **O** | Identifier → Type | Types of variables/attributes |
| **M** | (Class, Method) → Signature | Method signatures |
| **C** | (single class name) | Current class containing expression |

**Method signature:** Tuple of types `(T₁, T₂, ..., Tₙ, Tₙ₊₁)`
- T₁ through Tₙ: Parameter types
- Tₙ₊₁: Return type

**Dispatch rule:**

```
O, M, C ⊢ e₀ : T₀
O, M, C ⊢ e₁ : T₁
...
O, M, C ⊢ eₙ : Tₙ
M(T₀, f) = (T₁', T₂', ..., Tₙ', Tₙ₊₁')
T₁ ≤ T₁'
T₂ ≤ T₂'
...
Tₙ ≤ Tₙ'
─────────────────────────────────────────
O, M, C ⊢ e₀.f(e₁, ..., eₙ) : Tₙ₊₁'
```

**Breaking it down:**
1. Type the receiver `e₀` → get class `T₀`
2. Type each argument `eᵢ` → get types `Tᵢ`
3. Look up method `f` in class `T₀` → get signature `(T₁', ..., Tₙ', Tₙ₊₁')`
4. Check each argument is subtype of parameter: `Tᵢ ≤ Tᵢ'`
5. Return type is method's declared return type `Tₙ₊₁'`

**Why C (current class)?**
- Resolve `SELF_TYPE` (refers to class containing the expression)
- Handle `self.method()` calls
- Look up attributes accessed via `self`

**Complete typing judgment:**

```
O, M, C ⊢ e : T
```

"Under object environment O, method environment M, in class C, expression e has type T."

### Part 9: Implementation — From Rules to Code (Lecture 51)

**The algorithm:** Recursive descent over AST with two-phase pattern.

```python
def TypeCheck(env: Env, expr: Expr) -> Type:
    match expr:
        case IntLiteral(n):
            return Int
        
        case Identifier(name):
            return env.O.lookup(name)
        
        case Plus(e1, e2):
            t1 = TypeCheck(env, e1)
            t2 = TypeCheck(env, e2)
            if t1 != Int or t2 != Int:
                error("+ requires Int operands")
            return Int
        
        case Let(x, T, init, body):
            t0 = TypeCheck(env, init)
            if not subtype(t0, T):
                error(f"{t0} is not a subtype of {T}")
            env_new = env.extend(x, T)
            return TypeCheck(env_new, body)
        
        case Dispatch(receiver, method, args):
            t0 = TypeCheck(env, receiver)
            arg_types = [TypeCheck(env, arg) for arg in args]
            sig = env.M.lookup(t0, method)
            for (actual, formal) in zip(arg_types, sig.params):
                if not subtype(actual, formal):
                    error(f"Argument type mismatch")
            return sig.return_type
```

**Key patterns:**

1. **Environment flows down:** Passed to all recursive calls, extended for `let`
2. **Types flow up:** Returned from recursive calls, combined at parent
3. **Rules → code:** Each inference rule becomes a case
4. **Premises → checks:** If premises fail, report type error

**Error checking:**

Type checker must detect and report **all** type errors in source, including:
- Undeclared identifiers
- Type mismatches in operations
- Wrong number/types of arguments
- Invalid subclass relationships

**Don't fail fast — collect all errors!** Better UX.

**Chess engine analogy:**
- **Type checking traversal:** Like perft testing — visit every legal position
- **Error reporting:** Like illegal move detection — collect all violations
- **Environment passing:** Like incremental position updates (efficient)

## Key Insights

### 1. CFGs Hit a Wall — Context Matters
Context-free grammars **cannot express context-sensitive constraints**. "Variable declared before use" requires tracking state across the tree — that's not context-free. Semantic analysis fills this gap.

### 2. Scope is Context-Sensitive Analysis
When the meaning of `x` depends on **where** it appears (not what it says), you've left the realm of pure syntax. Symbol tables track this context.

### 3. Multiple Passes Are OK — Embrace Them
Cool needs three passes (classes, inheritance, types). Fighting for one pass creates complexity. Simple passes that compose are better.

### 4. Three Environments for Complete Context
- **O** (Objects): What variables exist and their types
- **M** (Methods): What methods exist and their signatures  
- **C** (Current class): Where am I in the class hierarchy

All three needed for method dispatch.

### 5. Inference Rules → Direct Implementation
Type rules translate **almost directly** to code:
- Each rule becomes a match case
- Premises become recursive calls
- Conclusion becomes return type

**This pattern works:** Formalism guides implementation.

### 6. Subtyping Enables Polymorphism Safely
`Dog ≤ Animal` lets you use dogs where animals expected, **without runtime checks**. The compiler guarantees safety, runtime just works.

### 7. Two-Phase Pattern Is Universal
- **Down:** Context flows to children (environments, scopes)
- **Up:** Results flow to parent (types, code)

Appears in type checking, code generation, optimization — it's fundamental.
