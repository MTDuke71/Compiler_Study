## Session Notes

### Runtime Organization (Lectures 52-54)

**The fundamental question:** Where does program state live?

**Two regions:**
- **Stack:** Activation records (stack frames) for function calls
  - Local variables
  - Parameters
  - Return addresses
  - Saved registers
  - Grows/shrinks automatically with calls/returns

- **Heap:** Dynamically allocated objects
  - Created via `new` (Cool), `malloc` (C)
  - Lives beyond function scope
  - Requires garbage collection or manual `free()`

**Key insight:** The stack/heap split isn't arbitrary — it's driven by **lifetime requirements**:
- Scope-bound data → stack (automatic)
- Persistent data → heap (manual/GC)

**Chess engine analogy:**
- **Stack:** Like the game's move history (push on move, pop on unmake)
- **Heap:** Like the transposition table (persists across moves, allocated once)

### Method Dispatch (Lectures 55-57)

**Static vs. Dynamic dispatch:**

| Type | When Decided | Mechanism | Example |
|------|-------------|-----------|---------|
| **Static** | Compile time | Direct call address | C functions, Java `private`/`final` |
| **Dynamic** | Runtime | Vtable lookup | C++ `virtual`, Java methods, Cool dispatch |

**Vtable (virtual method table):**
```
Dog object:
┌──────────────┐
│ vtable ptr   │──→ Dog vtable:
├──────────────┤   ┌─────────────┐
│ name: String │   │ speak() ──→ Dog.speak
├──────────────┤   │ walk() ───→ Animal.walk
│ age: Int     │   │ getName()→ Animal.getName
└──────────────┘   └─────────────┘
```

**Why vtables?** O(1) dispatch — one indirect jump, no searching.

**AoC analogy:**
- Static dispatch = direct function call (you know the path)
- Dynamic dispatch = lookup table (check which variant applies)

### Code Generation (Lectures 58-60)

**Template-based approach:** Each AST node type → instruction sequence template

```python
def codegen(expr: Expr) -> str:
    match expr:
        case IntLiteral(n):
            return f"li $a0, {n}"  # Load immediate

        case Plus(e1, e2):
            code1 = codegen(e1)     # Left → $a0
            code2 = codegen(e2)     # Right → $a0 (overwrites!)
            return f"""
                {code1}
                sw $a0, 0($sp)      # Save left result
                addiu $sp, $sp, -4  # Push stack
                {code2}
                lw $t1, 4($sp)      # Restore left
                add $a0, $t1, $a0   # Add
                addiu $sp, $sp, 4   # Pop stack
            """
```

**Key patterns:**
1. **Accumulator convention:** Result in `$a0` by convention
2. **Stack for temporaries:** Save intermediate values
3. **Recursive codegen:** AST structure drives code structure
4. **Post-order traversal:** Children first, parent combines

**Chess engine parallel:**
- **Codegen templates:** Like move generation templates (pawn moves, knight jumps)
- **Register allocation:** Like efficient board representation (bitboards vs mailbox)

### Register Allocation (Lectures 61-63)

**The problem:** Program assumes infinite registers; CPU has ~32.

**Graph coloring approach:**
1. Build **interference graph:** Nodes = variables, edges = "live at same time"
2. **Color the graph:** Each color = a register
3. If colorable with k colors → fits in k registers
4. Otherwise, **spill** some variables to stack

**Simplified example:**
```
a = 1
b = 2
c = a + b  # a, b both live here (interfere)
d = a + 5  # a, c live (c, d interfere if c still needed)
```

Interference graph:
```
a --- c
|     |
b     d
```

Can color with 2 colors (registers): {a, d} = R1, {b, c} = R2

**Why graph coloring?** NP-hard in general, but good heuristics exist (like Chaitin's algorithm).

**Spilling:** If can't color, pick a variable to keep in memory instead of register.

## Additional Work: Zettel Creation

### Z0022: Stack and Heap Allocation

Created comprehensive zettel documenting:
- **How stack size is determined:** Linker embeds size in executable, OS allocates at load time
- **How heap grows:** Dynamic allocation via `malloc()` → `brk()`/`mmap()` syscalls
- **Classic mental model:** "Stack grows down, heap grows up"
- **Modern reality:** 64-bit address spaces (128 TB), ASLR, multiple heap regions
- **Platform differences:** Windows inverts the layout! (empirically verified)
- **Compiler's role:** Stack frame layout at compile time, heap management at runtime

**Empirical testing:** Compiled and ran `memory-layout.c` to observe actual addresses:
```
Text (code):   0x7FF66B521000  ← Highest (Windows)
Heap:          0x1D15BFC8EE0   ← Middle
Stack:         0xB31E55F910     ← Lowest
```

**Key insight:** Stack/heap allocation is a **compile-time vs runtime** split:
- Stack: Fixed size, decided by linker/OS before program runs
- Heap: Variable size, grows on demand via OS calls during execution

**Chess engine analogy:**
- Stack = Opening book (fixed size, pre-allocated, fast)
- Heap = Transposition table (dynamic size, allocated as needed)

## Key Insights

### 1. Runtime Organization Mirrors Static Structure
Activation records (stack frames) **correspond exactly to function calls**. The call stack is the runtime manifestation of the call graph. Static analysis (type checking) and runtime organization (stack frames) are two views of the same structure.

### 2. Stack/Heap Split is Driven by Lifetime
Not arbitrary! Scope-bound data (locals, parameters) → stack. Data that outlives functions → heap. The compiler decides based on escape analysis.

### 3. Vtables Enable O(1) Dynamic Dispatch
Polymorphism doesn't require searching — one vtable pointer per object, one indirect jump. Minimal overhead for maximum flexibility.

### 4. Code Generation is Recursive Over AST
Just like parsing (CFG → AST) and type checking (AST → types), codegen is AST → instructions. The tree structure drives everything.

### 5. Register Allocation is Graph Coloring
**Liveness analysis** (when variables are used) creates the interference graph. Graph coloring assigns registers. If unsuccessful, spill to stack. Classic CS problem with practical compilers.

### 6. The Classic Stack/Heap Model is Oversimplified
On modern 64-bit systems with ASLR:
- Stack and heap are **nowhere near each other** (120+ TB gap)
- Layout is **randomized** each run (security)
- Heap uses **multiple strategies** (brk for small, mmap for large)
- **Platform-specific** (Windows inverts the traditional model)

But the simple model is still pedagogically valuable for understanding allocation speed, overflow behavior, and fragmentation.

### 7. Measurement Over Assumption
Running `memory-layout.c` revealed Windows's inverted layout — something not obvious from theory alone. Always verify assumptions with empirical testing (AoC lesson: measure, don't guess).
