## Three-Letter Acronyms (TLAs)

### AST — Abstract Syntax Tree
A tree representation of source code structure where:
- Each node represents a language construct (expression, statement, declaration)
- Leaves are terminals (literals, identifiers)
- Internal nodes are operators/control structures
- See: [[01-foundations/day-02-from-text-to-structure]]

### CFG — Control Flow Graph
A directed graph showing:
- Nodes = basic blocks (sequences of instructions)
- Edges = possible control flow between blocks
- Entry/exit points clearly marked
- Essential for optimization analysis
- See: [[05-ir/cfg]]

### CSE — Common Subexpression Elimination
An optimization that:
- Identifies duplicate computations
- Computes them once and reuses the result
- Example: `a*b + a*b` → `temp = a*b; temp + temp`
- See: [[06-optimization/README]]

### DAG — Directed Acyclic Graph
A graph with:
- Directed edges (one-way arrows)
- No cycles (can't return to a node following edges)
- Used in dependency analysis and expression optimization

### DCE — Dead Code Elimination
An optimization that removes:
- Unreachable code (never executed)
- Code whose results are never used
- Variables that are written but never read
- See: [[06-optimization/dead-code]]

### DFA — Deterministic Finite Automaton
A state machine where:
- For each state and input, there's exactly one next state
- Used to recognize tokens in lexical analysis
- More efficient than NFAs for execution
- See: [[02-lexing/regular-languages]]

### GVN — Global Value Numbering
An optimization technique that:
- Assigns numbers to expressions based on computed values
- Identifies equivalent expressions across basic blocks
- More powerful than local CSE

### LVN — Local Value Numbering
Like GVN but:
- Only within a single basic block
- Simpler to implement
- Less powerful but faster

### NFA — Nondeterministic Finite Automaton
A state machine where:
- Multiple next states possible for same input
- Can have epsilon transitions (no input consumed)
- Easier to construct from regex than DFA
- See: [[02-lexing/regular-languages]]

### SSA — Static Single Assignment
An IR property where:
- Each variable is assigned exactly once in the code
- Use phi-functions at merge points
- Makes data flow analysis simpler
- See: [[05-ir/ssa-intuition]]

### TAC — Three-Address Code
An IR format where:
- Each instruction has at most 3 addresses (result, operand1, operand2)
- Example: `t1 = a + b` instead of nested expressions
- Linear representation, easier to optimize than trees
- See: [[05-ir/three-address-code]]

## Formal Language Concepts

### Chomsky Hierarchy
A classification of formal grammars ordered by expressive power:

**Type 3 (Regular):** Recognized by finite automata; no memory; used for lexical analysis (tokens, identifiers)

**Type 2 (Context-Free):** Recognized by pushdown automata; one stack; used for parsing (nested structures, expressions)

**Type 1 (Context-Sensitive):** Recognized by linear-bounded automata; context-dependent rules; used for semantic constraints

**Type 0 (Unrestricted):** Recognized by Turing machines; parsing is undecidable; impractical for compilers

**Key insight:** Each compiler phase uses exactly the minimum level needed—lexing uses Type 3, parsing uses Type 2, semantics needs Type 1.

**Fundamental limitation:** Finite automata (Type 3) cannot recognize balanced parentheses (need arbitrary counting). This is mathematical, not a limitation of implementation.

See detailed analysis: [[zettel/Z0007-chomsky-hierarchy]]

## Parsing Algorithms

### LL — Left-to-right, Leftmost derivation
- Top-down parsing
- Predicts production based on lookahead
- LL(k) = k tokens of lookahead
- Easier to implement by hand
- See: [[03-parsing/recursive-descent]]

### LR — Left-to-right, Rightmost derivation
- Bottom-up parsing
- Shift-reduce algorithm
- More powerful than LL
- Usually generated by tools

### LALR — Look-Ahead LR
- Optimized version of LR
- Used by tools like Yacc/Bison
- Good balance of power and efficiency

### PEG — Parsing Expression Grammar
- Alternative to context-free grammars
- Ordered choice (first match wins, no ambiguity)
- Unlimited lookahead with backtracking
- Can recognize some non-context-free languages
- Packrat parsing provides linear time guarantee
- Sometimes combines lexing and parsing (scanner-less)
- Examples: PEG.js, Pest, Python's new parser
- See: [[03-parsing/README]]

### SLR — Simple LR
- Simplified LR parsing
- Less powerful than LALR
- Easier to understand conceptually

## Compiler Phases

### Lexing (Lexical Analysis)
- Input: Character stream
- Output: Token stream
- Recognizes words, numbers, operators
- See: [[02-lexing/README]]

### Parsing (Syntax Analysis)
- Input: Token stream
- Output: AST
- Verifies grammatical structure
- See: [[03-parsing/README]]

### Semantic Analysis
- Input: AST
- Output: Annotated AST + symbol table
- Type checking, scope resolution
- See: [[04-semantics/README]]

### IR Generation
- Input: Annotated AST
- Output: Intermediate Representation
- Platform-independent code form
- See: [[05-ir/README]]

### Optimization
- Input: IR
- Output: Optimized IR
- Improves performance, reduces size
- See: [[06-optimization/README]]

### Code Generation
- Input: Optimized IR
- Output: Target code (assembly/machine code)
- Register allocation, instruction selection
- See: [[07-codegen/README]]

## Key Concepts

### Basic Block
A sequence of instructions with:
- One entry point (at beginning)
- One exit point (at end)
- No branches in middle
- Fundamental unit in CFG

### Dominance
In a CFG, node A **dominates** node B if:
- Every path from entry to B passes through A
- Critical for SSA construction
- See: [[05-ir/ssa-intuition]]

### First Set
In parsing, First(α) is:
- The set of terminals that can begin strings derived from α
- Used in LL parser construction
- See: [[03-parsing/README]]

### Follow Set
In parsing, Follow(A) is:
- The set of terminals that can appear immediately after nonterminal A
- Used in LL parser construction
- See: [[03-parsing/README]]

### Graph Coloring
A register allocation algorithm:
- Model registers as colors, variables as graph nodes
- Connect nodes if variables are live at same time (interference)
- Goal: Color graph with K colors (K = number of registers)
- Nodes that "interfere" must have different colors (registers)
- More complex than linear scan but produces better code
- Used in GCC, LLVM for optimized builds
- See: [[07-codegen/registers-are-scarce]]

### Invariant
A property that must remain true:
- Throughout a transformation
- Across all valid states
- Contracts between compiler phases
- See: [[00-index/invariants]] [[zettel/Z0004-invariants]]

### Left Recursion
A grammar rule where:
- A nonterminal can derive itself as leftmost symbol
- Example: `E → E + T`
- Must be eliminated for LL parsing
- See: [[03-parsing/README]]

### Phi Function
In SSA form:
- Special function at CFG merge points
- Selects value based on incoming edge
- Example: `x = φ(x₁, x₂)` means x comes from x₁ or x₂
- See: [[05-ir/ssa-intuition]]

### Register Spilling
When there aren't enough registers:
- Store values to memory (stack)
- Load them back when needed
- Performance cost
- See: [[07-codegen/registers-are-scarce]]

### Symbol Table
A data structure tracking:
- Variable names and their properties
- Scope information
- Type information
- Declaration locations
- See: [[04-semantics/symbol-tables]]

### Token
The output unit of lexical analysis:
- Type (identifier, number, operator, keyword)
- Value (lexeme)
- Position (line, column)
- See: [[02-lexing/tokens-vs-characters]]

## Common Terminology

### Associativity
Whether operators group left-to-right or right-to-left:
- **Left**: `a - b - c` = `(a - b) - c`
- **Right**: `a = b = c` = `a = (b = c)`
- See: [[03-parsing/precedence-and-associativity]]

### Precedence
Operator priority in parsing:
- Highnear Scan Allocation
A simple register allocation algorithm:
- Single pass through instructions in order
- Assign registers as variables become live
- Spill to memory when out of registers
- Fast to compile (~200 lines of code)
- 95% as good as graph coloring in practice
- Used in V8, HotSpot, LuaJIT (production JITs)
- See: [[07-codegen/registers-are-scarce]]

### Lier precedence binds tighter
- Example: `*` before `+` means `2 + 3 * 4` = `2 + (3 * 4)`
- See: [[03-parsing/precedence-and-associativity]]

### Lexeme
The actual text matched by a token:
- Token type: IDENTIFIER
- Lexeme: "count"
- See: [[02-lexing/tokens-vs-characters]]

### Liveness
A variable is **live** at a point if:
- Its value may be used later
- It hasn't been overwritten
- Critical for register allocation
- See: [[06-optimization/data-flow]]

### Reaching Definition
A definition (assignment) **reaches** a point if:
- The value might be used there
- It hasn't been overwritten on some path
- Used in data flow analysis
- See: [[06-optimization/data-flow]]

### Scope
The region where a name binding is valid:
- Lexical scope: Determined by source code structure
- Dynamic scope: Determined by runtime call stack
- See: [[04-semantics/scope]]

### Use-Def Chain
A data structure linking:
- Each **use** of a variable
- To its possible **definitions**
- Essential for optimization

### Def-Use Chain
The reverse of use-def:
- Each **definition** of a variable
- To all its possible **uses**

## State & Representation

### State
The configuration of a system at a point in execution:
- Variable values
- Control location
- Memory contents
- See: [[zettel/Z0001-state]] [[01-foundations/language-as-state]]

### Representation
How information is encoded:
- Concrete syntax (source code text)
- Abstract syntax (AST)
- Intermediate forms (IR)
- Machine code

## Additional Notes

### Acronyms to Remember
- **IR** = Intermediate Representation (general term)
- **IC** = Intermediate Code (similar to IR)

- **LLVM IR** = LLVM's intermediate representation

- **opt** = optimization
- **expr** = expression
- **stmt** = statement
- **decl** = declaration
- **def** = definition
- **temp** = temporary variable
